The CLI uses a **TypeScript configuration file** with full IntelliSense via `defineConfig()`.

| File | Purpose |
|---|---|
| `./supercheck.config.ts` | Project configuration (checked into the repo) |
| `./supercheck.config.local.ts` | Local overrides (gitignored, optional) |

<Callout type="warn">
Config files must **never** contain tokens. The CLI scans for token patterns (`sck_live_*`, `sck_trigger_*`, `sck_test_*`) and rejects any config containing them.
</Callout>

The CLI rejects unknown keys in typed configuration sections so misspellings surface during `config validate` or a sync operation. Provider-specific `config` maps remain extensible.

## Full Example

```ts title="supercheck.config.ts"
import { defineConfig } from '@supercheck/cli'

export default defineConfig({

  project: {
    organization: '019c1fe3-0a0a-7ae9-884d-61baea139786',
    project: '019c1fe3-0a0f-7089-97b3-12990d78a9ee',
  },
  api: {
    baseUrl: process.env.SUPERCHECK_URL ?? 'https://app.supercheck.io',
  },
  tests: {
    playwright: {
      testMatch: '_supercheck_/playwright/**/*.pw.ts',
    },
    k6: {
      testMatch: '_supercheck_/k6/**/*.k6.ts',
    },
  },
  monitors: [
    {
      id: '019c3643-9495-7d66-a463-1c0d42d4520e',
      name: 'API Health Monitor',
      type: 'http_request',
      target: 'https://api.example.com/health',
      frequencyMinutes: 5,
      enabled: true,
      config: {
        method: 'GET',
        timeoutSeconds: 30,
        expectedStatusCodes: '200-299',
        locationConfig: {
          locations: ['local'],
        },
      },
      alertConfig: {
        enabled: true,
        alertOnFailure: true,
        alertOnRecovery: true,
        notificationProviders: ['019c22b5-6df9-79b7-b415-db8317b1bd0b', '019c22b5-a812-7acc-9f23-46f7904d2c2a'],
      },
      tags: ['api', 'production'],
    },
  ],
  requirements: [
    {
      title: 'Homepage loads for anonymous visitors',
      description: 'The marketing homepage renders without errors.',
      priority: 'high',
      tags: ['web', 'smoke'],
      externalId: 'PROJ-123',
      externalUrl: 'https://tracker.example.com/PROJ-123',
      tests: ['_supercheck_/playwright/homepage-check.019a1234-abcd-7000-8000-000000000001.pw.ts'],
    },
  ],
  statusPages: [
    {
      name: 'Example Status',

        { name: 'API', description: 'Public REST API', monitors: ['API Health Monitor'], position: 0 },

        enabled: true,
        alertOnFailure: true,
        alertOnSuccess: true,
        notificationProviders: ['019c22b5-6df9-79b7-b415-db8317b1bd0b'],
      },
    },
  ],
})
```

## Precedence

Settings resolve in this order, highest priority first:

| # | Source | Examples |
|---|---|---|
| 1 | **CLI flags** | `--url`, `--config` |
| 2 | **Environment variables** | `SUPERCHECK_URL`, `SUPERCHECK_ORG`, `SUPERCHECK_PROJECT` |
| 3 | **`supercheck.config.local.ts`** | Local overrides (deep-merged) |
| 4 | **`supercheck.config.ts`** | Project defaults |

To use a specific file (`.ts`, `.js` or `.mjs`): `supercheck deploy --config ./configs/staging.config.ts`

## Project Structure

Tests live in `_supercheck_/`, grouped by runner:

```
my-project/
├── _supercheck_/
│   ├── playwright/
│   │   ├── homepage-check.019a1234-abcd-7000-8000-000000000001.pw.ts   # Playwright test (slug + UUID)
│   │   └── api-check.019a1234-abcd-7000-8000-000000000002.pw.ts        # Playwright API test
│   ├── k6/
│   │   └── load-test.019a1234-abcd-7000-8000-000000000003.k6.ts        # k6 performance test
├── supercheck.config.ts
└── package.json
```

| Extension | Runner | Example |
|---|---|---|
| `*.pw.ts` | Playwright | `_supercheck_/playwright/homepage-check.019a1234-abcd-7000-8000-000000000001.pw.ts` |
| `*.k6.ts` | k6 | `_supercheck_/k6/load-test.019a1234-abcd-7000-8000-000000000003.k6.ts` |

<Callout type="info">
Test files pulled from the cloud use `slug.{uuid}.pw.ts` and `slug.{uuid}.k6.ts`. The UUID keeps paths stable across renames, while the slug makes files easy to identify locally.
</Callout>

### Test metadata annotations

`supercheck pull` writes `// @title`, `// @priority` (`low`, `medium`, `high`) and `// @tags` (comma-separated tag names) in the header of each test script: the leading run of `//` lines, or inside a multi-line JSDoc block at the very top (a single-line `/** ... */` header is left alone). `@priority` and `@tags` elsewhere in the script are ignored; `@title` is read from the first match anywhere. They are local metadata: the CLI strips them before comparing or sending the script, including with `test create --file` and `test update --file`. `deploy` applies `@priority` (any letter case) and `@tags`; if an annotation is absent, the remote value is left alone. To remove all tags from a test, use `supercheck test tag remove`.

```ts
// @title Homepage Check
// @priority high
// @tags smoke, web
```

## Validate and Deploy

| Command | What it does |
|---|---|
| `supercheck config validate` | Validate config syntax and schema |
| `supercheck config print` | Print the resolved configuration (with env var expansion) |
| `supercheck diff` | Preview changes between config and server state |
| `supercheck deploy` | Create/update resources; `--dry-run` previews, `--delete` removes remote resources absent from config, `--force` skips confirmation |
| `supercheck destroy` | Tear down all managed resources; `--dry-run` previews, `--force` confirms |

Resources are reconciled by database `id`. Pulled resources include their `id` (UUID); new resources omit it and are created on deploy. `diff` includes notification provider settings such as webhook `bodyTemplate`, so review it before deploying and keep test scripts as editable source files.

`diff` and `deploy` preserve remote resources absent from config by default. Use `diff --delete` to preview pruning, then `deploy --delete` to apply it. Pruning includes resources created outside this config. `--no-delete` remains supported.

Before sync operations, the CLI verifies configured organization and project IDs or slugs against the authenticated API context, catching config that would point at a different project than the token.

## Schema Reference

<Accordions>
<Accordion title="project and api" id="project">

**`project`**

| Field | Type | Required | Description |
|---|---|---|---|
| `organization` | `string` | Yes | Organization ID or slug |
| `project` | `string` | Yes | Project ID or slug |

**`api`**

| Field | Type | Default | Description |
|---|---|---|---|
| `baseUrl` | `string` | `https://app.supercheck.io` | API base URL |

**`defaults`** (reserved for future use: defined in the schema but not currently applied during local CLI execution)

| Field | Type | Description |
|---|---|---|
| `runLocation` | `string` | Default worker routing code (e.g. `local`) |
| `timeout` | `number` | Default execution timeout in milliseconds |

</Accordion>
<Accordion title="tests.playwright and tests.k6" id="tests-playwright">

| Field | Type | Description |
|---|---|---|
| `tests.playwright.testMatch` | `string` | Glob pattern for Playwright test files |
| `tests.playwright.browser` | `string` | Browser for local execution (`chromium`, `firefox`, or `webkit`; default `chromium`) |
| `tests.k6.testMatch` | `string` | Glob pattern for k6 test files |

</Accordion>
<Accordion title="jobs[]" id="jobs">

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Database UUID (present for existing resources, omit for new) |
| `name` | `string` | Job display name |
| `jobType` | `string` | Job runner type (`playwright`, `k6`) |
| `cronSchedule` | `string` | Cron expression |
| `tests` | `string[]` | Test file paths or IDs |
| `alertConfig` | `object` | Alert config with `notificationProviders` (UUIDs), `alertOnFailure`, etc. Incident fields: `incidentEnabled`, `incidentSeverity`, `autoResolveIncident` (see below) |

</Accordion>
<Accordion title="monitors[]" id="monitors">

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Database UUID (present for existing resources, omit for new) |
| `name` | `string` | Monitor display name |
| `type` | `string` | `http_request`, `website`, `ping_host`, `port_check`, `synthetic_test` |
| `target` | `string` | URL or host to monitor |
| `frequencyMinutes` | `number` | Check interval in minutes |
| `enabled` | `boolean` | Whether the monitor is active |
| `config` | `object` | Monitor-specific config (`method`, `timeoutSeconds`, `expectedStatusCodes`, `locationConfig`) |
| `alertConfig` | `object` | Alert config with `notificationProviders` (UUIDs), `alertOnFailure`, `alertOnRecovery`. Incident fields: `incidentEnabled`, `incidentSeverity`, `autoResolveIncident` (see below) |
| `tags` | `string[]` | Tag names assigned to the monitor. Omit to leave remote tags unchanged; names compare case-insensitively and must exist in the project or under `tags[]` |

Jobs have no `tags` field; a config containing one fails validation.

### Incident fields in `alertConfig`

| Field | Type | Default | Description |
|---|---|---|---|
| `incidentEnabled` | `boolean` | `true` | Open an incident when the check alerts |
| `incidentSeverity` | `string` | auto | `sev1` to `sev4`. Omit to derive severity from the alert |
| `autoResolveIncident` | `boolean` | `true` | Resolve the incident when the check recovers, if nobody acknowledged it |

</Accordion>
<Accordion title="requirements[]" id="requirements">

Needs a server with the requirements API. Remote requirements are compared, and pruned by `deploy --delete`, only when the config has a `requirements` key; a config without one leaves dashboard requirements alone. Omitting `description`, `priority`, `externalId` or `externalUrl` leaves the remote value unchanged. Set `description`, `priority`, `externalId` or `externalUrl` to `""` to clear it.

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Database UUID (present for existing resources, omit for new) |
| `title` | `string` | Required, 1-500 characters |
| `description` | `string` | Requirement description |
| `priority` | `string` | `low`, `medium`, `high`; `""` clears it |
| `tags` | `string[]` | Tag names (max 10, 50 characters each). Omit to leave remote tags unchanged; `[]` clears them. Names compare case-insensitively; missing tags are created by the server |
| `externalId` | `string` | ID in an external tracker (max 255 characters) |
| `externalUrl` | `string` | `http://` or `https://` URL in an external tracker |
| `tests` | `string[]` | Linked tests, referenced like a job's `tests` (file path, filename or UUID; max 100). Omit to leave remote links unchanged; `[]` unlinks all |

</Accordion>
<Accordion title="statusPages[]" id="statuspages">

Needs a server with the status page write API. `config validate` checks the server's length limits and formats, so most bad values fail before anything is written; the server stays the final check (for example, custom domain availability on your plan). Omitting a field leaves the remote value unchanged; `""` clears `headline`, `description`, `supportUrl` or `customDomain`.

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Database UUID (present for existing resources, omit for new) |
| `name` | `string` | Status page display name (max 255 characters) |
| `subdomain` | `string` | Read-only. Written by `pull`, never compared or sent (the server generates it) |
| `status` | `string` | `draft`, `published`, `archived` |
| `headline` | `string` | Public page headline (max 255 characters) |
| `description` | `string` | Public description text (max 2000 characters) |
| `supportUrl` | `string` | Support contact: an email address or an `http(s)`/`mailto:` URL (max 500 characters) |
| `language` | `string` | Language code such as `en` or `pt-BR` |
| `timezone` | `string` | Timezone name (max 50 characters, e.g. `UTC`) |
| `customDomain` | `string` | Custom domain such as `status.example.com` |
| `branding` | `object` | Colors, each `#RRGGBB`: `bodyBackgroundColor`, `fontColor`, `lightFontColor`, `greens`, `yellows`, `oranges`, `blues`, `reds`, `borderColor`, `graphColor`, `linkColor`, `noData` |
| `notifications` | `object` | Boolean toggles with no defaults: `allowPageSubscribers`, `allowEmailSubscribers`, `allowWebhookSubscribers`, `allowSlackSubscribers`, `allowIncidentSubscribers`, `allowRssFeed`. Omitted flags are left unchanged |
| `components` | `object[]` | Components (see below) |

Each entry in `components`:

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Database UUID (omit for new) |
| `name` | `string` | Component name (max 255 characters, unique within the page) |
| `description` | `string` | Component description (max 2000 characters; omit to leave unchanged, `""` clears it) |
| `monitors` | `string[]` | Up to 100 monitor UUIDs, or names of monitors defined in this config. Deploy checks that each one exists before writing. Omit to leave links unchanged; `[]` unlinks all |
| `position` | `number` | Display order (integer, 0 to 1000) |

When the page declares `components`, remote components missing from that list are removed only when you run `deploy --delete`. Omitting `components` leaves every remote component alone, even with `--delete`. A new page with `status: 'published'` must declare at least one component.

</Accordion>

<Accordion title="notificationProviders[]" id="notificationproviders">

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Database UUID |
| `name` | `string` | Provider display name |
| `type` | `string` | `email`, `slack`, `webhook`, `telegram`, `discord`, `teams` |
| `config` | `object` | Provider-specific configuration, including webhook `method`, `headers` and `bodyTemplate` |

`pull` omits masked provider secrets such as webhook URLs and credentials. You can still edit non-secret settings such as `bodyTemplate`; `diff` detects those changes without exposing stored secrets.

If you explicitly supply provider credentials in config, those values can still produce an update plan. Review provider changes in `diff` before deploying; do not assume a config containing secrets is treated as unchanged.

For webhook providers, `config.bodyTemplate` is part of the managed configuration and should be kept in source control with the rest of the provider config. `supercheck pull` exports it, `supercheck diff` reports edits to it, and `supercheck deploy` applies them as provider configuration changes.

To edit a pulled provider:

1. Change non-secret settings such as `bodyTemplate` in the configuration file.
2. Leave omitted secret fields out of the file to preserve their existing values.
3. Run `supercheck diff`, review the changes, then deploy.

To rotate a credential, enter its replacement in the dashboard or use `supercheck notification update --config` with the full replacement config. If you supply a replacement through monitoring-as-code, keep that value out of source control; `diff` redacts the secret change.

## Deployment State

Successful deploys record server-assigned IDs for created resources, and the current names of updated or unchanged managed resources, in `supercheck.state.json`. Commit and share this file with CI so later deployments manage the same resources. Do not commit the temporary `supercheck.state.json.lock`.

<Accordions>
<Accordion title="State file and ownership details" id="state-details">

The mapping is scoped to the API origin and the actual organization and project returned by the server, and tracks replacement IDs when a managed remote resource is deleted and recreated. `diff` and dry runs do not persist state. The `.lock` file coordinates deploys only on a shared local filesystem.

Names alone never establish ownership. If a same-name remote resource has no ID in the local config or state file, deploy stops and asks you to pull the resource or provide its explicit ID. Renaming an ID-less non-test resource creates a separate resource; the old remote resource remains unless you deploy with `--delete`. Carry its explicit ID or pull it first to update the existing resource. Deploy resolves newly created test IDs before dependent jobs and synthetic monitors, and preserves local test file paths instead of renaming them after deployment. Monitor and job tag assignments are rejected before writes; standalone tag CRUD remains supported.

</Accordion>
<Accordion title="Offline validation and pull behavior" id="offline-and-pull">

`config validate --offline` and `config print --offline` support local-only configurations without API credentials, but still require an existing config file. By contrast, `test run --offline --file <path>` can run without a config file.

During pull, managed test paths and existing browser and `testMatch` settings are preserved. Runner-type changes migrate files with backups; new tests must match configured custom globs or pull stops before writing. Backups are retained and must be removed manually when no longer needed.

</Accordion>
<Accordion title="Self-hosted and proxy" id="self-hosted-configuration">

Cloud users need no URL setting. For a self-hosted instance, use its HTTPS URL (see the [production deployment guide](/docs/app/deployment/self-hosted) if it is not configured yet):

```bash
export SUPERCHECK_URL="https://supercheck.yourdomain.com"
export SUPERCHECK_TOKEN="sck_live_..."

supercheck whoami
```

If using the Cloudflare proxy, set SSL/TLS mode to "**Full (strict)**" in the Cloudflare dashboard.

For environments behind HTTP proxies:

```bash
export HTTPS_PROXY="http://proxy.corp.com:8080"
export NO_PROXY="localhost,127.0.0.1,.internal.corp.com"
export SUPERCHECK_TRIGGER_KEY="sck_trigger_..."
export SUPERCHECK_TOKEN="sck_live_..."

supercheck job trigger abc123 --wait
```
