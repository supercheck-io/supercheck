| I want to | Run |
|---|---|
| Sign in | `supercheck login` |
| See what to do next in a repo | `supercheck onboard` |
| Run tests locally, no account | `supercheck test run --offline --all` |
| Preview and publish config | `supercheck diff`, `supercheck deploy --dry-run`, then `supercheck deploy` |

## Global flags

Available on all commands, before or after the subcommand, for example `supercheck --json job trigger <job-id> --wait`.

| Flag | Description |
|---|---|
| `--json` | JSON output for scripting |
| `--envelope` | Include pagination metadata with JSON list results; requires `--json` |
| `--show-secrets` | Disable redaction of sensitive fields |
| `--quiet` | Only IDs and errors |
| `--wide` | Tables without width limits |
| `--no-color` | Disable ANSI colors |
| `--debug` | Debug logging |
| `-v`, `--version` | Show version |

Config-aware commands (`config`, `diff`, `deploy`, `pull`, `validate`, `destroy`) also accept `--config <path>`.

Delete commands (`job`, `test`, `monitor`, `run`, `requirement`, `var`, `tag`, `notification`) and `destroy` need project admin or higher.

<Accordions>
<Accordion title="JSON output and secret redaction" id="json-output">

- `sre ask`, `sre brief`, `run stream` and `test status` emit newline-delimited JSON (NDJSON), one event per line.
- List commands print a JSON array. Add `--envelope` for pagination metadata.
- Local test and job runs emit bounded NDJSON `local.result` records.
- Fatal errors go to stderr as JSON with `error`, `exitCode`, and API `status` and `details` when available.
- Sensitive fields are redacted by default: notification webhook URLs, Discord and Teams webhook credentials and provider config headers. Monitor target URLs stay visible and credential headers are masked. Use `--show-secrets` only when the output is handled securely.
- Creating a trigger key requires `--show-secrets` to show its one-time value. Without it the command fails before sending the request.

</Accordion>
<Accordion title="Terminal output details" id="investigation-status-and-terminal-output">

- Use `--wide` for unrestricted table values or `--json` for complete payloads. `--no-color` and `NO_COLOR` disable colors. Pipes get no colors or spinners, and closing a pipe early (`supercheck ... | head`) ends the command quietly.
- `config print` prints indented JSON with secret variable values masked.
- Test create and update summaries omit the script. `test get <id> --include-script` reads the decoded source, redacted unless you add `--show-secrets`.
- SRE output uses the same Field/Value tables as monitors, tests and jobs. Triage separates run metadata from the summary. Copilot answers and evidence briefs have report headings; `--quiet` suppresses their content. `--json` wins over `--quiet`.

</Accordion>
</Accordions>

## Exit codes

| Code | Meaning | Example |
|---|---|---|
| `0` | Success | Job completed |
| `1` | General error | Test failed, monitor down |
| `2` | Authentication error | Invalid or expired token |
| `3` | Configuration error | Missing config, invalid schema |
| `4` | Network or API error | API unreachable, 5xx |
| `5` | Timeout | Operation exceeded timeout, stream idle timeout |
| `130` | Interrupted | Ctrl+C during a stream |

An operation that needs confirmation exits `3` when declined or when input closes (`ABORTED`). In a non-interactive session it exits `3` with `CONFIRMATION_REQUIRED`. Review the plan, then pass `--force` to apply the authorized change.

## Agent-first operation

| Command | What it does | Key flags |
|---|---|---|
| `supercheck skills [topic]` | Print the offline workflow index or a focused guide: `onboarding`, `authoring`, `local`, `sync`, `configure`, `execute`, `ci`, `ship`, `safety`, `investigate`. Bundled with the CLI version; no credentials | — |
| `supercheck skills install` | Write a `.agents/skills/supercheck/SKILL.md` pointer. Existing files are kept unless `--force` | `--path <directory>`, `--force` |
| `supercheck capabilities` | Report CLI version, local capabilities and whether credentials are present | `--online` |
| `supercheck schema config` | Describe the installed configuration schema without loading repository code; the full structure with `--json` | `--json` |

`--online` verifies the API context with one request. It does not prove that every server feature is available or that the token may perform every operation.

### Machine-readable plans and writes

- `diff --json` and `deploy --dry-run --json` return plans on stdout.
- Successful deploys return per-resource results with server-assigned IDs and the state-file path.
- `pull --dry-run --json` describes the remote resources and config path it would write.
- Other mutation `--dry-run --json` commands return the proposed request payload.

JSON errors on stderr carry a stable `code` to branch on, plus `retryable` and suggested `nextActions` where useful.

| Code | Meaning |
|---|---|
| `AUTH_REQUIRED` | No credential; run `supercheck login` |
| `TOKEN_INVALID` | Credential expired, revoked or rejected; run `supercheck login --reauth` |
| `PERMISSION_DENIED` | Authenticated but not allowed (role or project) |
| `SUBSCRIPTION_REQUIRED` | No active plan; a person must choose one in the dashboard |
| `SPENDING_LIMIT_REACHED` | The organization's spending limit blocks execution |
| `RATE_LIMITED` / `SERVICE_UNAVAILABLE` | Retryable |
| `VALIDATION_FAILED` | The request was rejected as invalid |
| `CONFIRMATION_REQUIRED` | A write needs `--force` |
| `PAYMENT_REQUIRED` | The server answered 402 without a recognised reason; run `supercheck plan` |
| `AUTHORIZATION_PENDING` | `login` without `--json` or a terminal started a browser login that is not approved yet (exit `2`); approve it, then run `login` again |
| `DEVICE_CODE_DENIED`, `DEVICE_CODE_EXPIRED`, `DEVICE_CODE_CONSUMED`, `DEVICE_LOGIN_UNVERIFIED`, `TOKEN_LIMIT_REACHED` | Browser-login outcomes |
| `CONTEXT_MISMATCH` | The config's API URL, organization or project does not match the logged-in context; see `supercheck link` |

The CLI checks that the config's organization and project match the authenticated context before sync operations.

<Callout type="info">
Deploy records returned IDs in `supercheck.state.json`. Share it with CI so later deploys manage the same resources, and do not commit the transient `.lock` file. Names alone do not establish ownership: pull an existing resource or set its explicit ID. Deploy does not rename local test files.
</Callout>

## Authentication

| Command | What it does | Key flags |
|---|---|---|
| `supercheck login` | Sign in through your browser, or store a CLI token | `--token`, `--url`, `--reauth`, `--no-browser`, `--wait`, `--timeout` |
| `supercheck link` | Point `supercheck.config.ts` at the org and project you are logged in to | `--dry-run`, `--force`, `--config <path>` |
| `supercheck onboard` | Read-only status of the current directory and the single next command | — |
| `supercheck discover` | Bounded, read-only facts about the repository | `--root <directory>` |
| `supercheck plan` | Show whether the organization has an active subscription | — |
| `supercheck ci init --github` | Write `.github/workflows/supercheck.yml` | `--path <file>`, `--force` |
| `supercheck agent install` | Install the Supercheck skill for a coding agent | `--target`, `--path`, `--pointer`, `--force` |
| `supercheck whoami` | Show the authenticated project, role and token details | — |
| `supercheck logout` | Clear stored credentials | — |

`whoami` prints User, Token, API URL, Project, Role, Expires and Last used when your role may view API keys. The organization appears only with `--json`. A project viewer cannot sign in with the CLI, so it cannot use `whoami` either.

<Accordions>
<Accordion title="supercheck login: flags and browser sign-in" id="supercheck-login">

| Flag | Description |
|---|---|
| `--token <token>` | CLI token (`sck_live_*` or `sck_test_*`), verified against the API before it is stored. Without it, the CLI signs in through your browser when the server supports it |
| `--url <url>` | API base URL. Browser login uses `--url`, then `SUPERCHECK_URL`, then the stored URL, then the cloud default. With `--token`, the project config `api.baseUrl` is also tried after the stored URL |
| `--reauth` | Start a new browser login even if you are already signed in |
| `--no-browser` | Print the login URL and code without opening a browser |
| `--wait` | Wait for browser approval instead of returning immediately (default in an interactive terminal) |
| `--timeout <seconds>` | With `--wait`: give up after this long (30 to 3600, default 900); the login stays resumable. A dropped connection during the wait is retried until then |

**Browser login** is a device-authorization sign-in. The CLI prints a URL and a short code. You approve the request in the browser, choosing the project the CLI may access, and the CLI stores a project-scoped key that expires in 90 days. Only approve a code you just requested yourself. Enter the code from your terminal in the confirmation field; the info icon shows the request code and requester address.

- **Interactive terminal:** waits for approval and opens your browser.
- **Agents and scripts:** `supercheck login --json` prints the URL and code and returns immediately with `"state": "authorization_pending"`. Run it again after approval to finish. With `--wait` it blocks: it prints the pending object first, then a second JSON line with the result.
- **Precedence:** `SUPERCHECK_TOKEN`, if set, always wins over a stored login.
- **Plans (cloud only):** if the organization you pick has neither an active trial nor a paid plan, the approval page says so and, if you own the organization, offers **Choose a plan**. That makes the organization active and opens billing in a new tab, so the right organization is charged and your login code stays valid. Approving never depends on a plan: you can connect and run tests locally first. Cloud runs require an active trial or plan. Run `supercheck plan` afterwards to confirm.
- **Self-hosted:** if the server does not enable browser login, the command explains how to use `--token`. Point at your instance with `--url` or `SUPERCHECK_URL`.

</Accordion>
<Accordion title="supercheck link" id="supercheck-link">

Edits only the `organization` and `project` values and the default API URL written by `supercheck init`, and never executes the file. If the config already targets a different project it refuses with `CONTEXT_MISMATCH`. `--dry-run` shows the conflict without failing. `--force` replaces the existing values, so use it only after confirming the change.

</Accordion>
<Accordion title="supercheck onboard, discover and plan" id="supercheck-onboard">

- **`onboard`** never changes files or the cloud, so it is safe to repeat. It reports the state (`needs_init`, `needs_tests`, `needs_auth`, `needs_link`, `needs_plan`, `ready_to_deploy`, `deployed`) and the next command.
- **`discover`** reports package manager, framework, routes, existing Playwright and k6 tests, CI provider and the key names (never values) from `.env.example`. It does not run scripts, import configuration, read `.env` or follow symlinks.
- **`plan`** never treats an unknown result as free or paid.

</Accordion>
<Accordion title="supercheck ci init and agent install" id="supercheck-ci-init---github">

**`ci init --github`** writes a workflow where pull requests run tests locally without credentials and pushes to `main` deploy using the `SUPERCHECK_TOKEN` repository secret. It does not create that secret. Set a `SUPERCHECK_URL` repository variable only for a self-hosted instance. When it is unset or blank the CLI uses the API URL in `supercheck.config.ts` (Supercheck Cloud by default).

- The deploy job caches `supercheck.state.json` with `actions/cache`. Caches can be evicted, so also commit the file. A newly committed state starts a fresh cache chain because the key includes the file's hash.
- The workflow runs the locally installed CLI (`npx --no-install`, `pnpm exec` or `yarn`, matching your lockfile), so add `@supercheck/cli` as a devDependency.
- It refuses to overwrite an existing file without `--force`.

**`agent install`** installs the skill for `--target claude`, `cursor`, `codex`, `opencode` or `generic`. It never overwrites existing files without `--force`. `--pointer AGENTS.md` adds a short block delimited by markers and only ever rewrites that block.

| Target | Installed to |
|---|---|
| `claude` | `.claude/skills/supercheck/SKILL.md` |
| `cursor` | `.cursor/rules/supercheck.mdc` |
| `codex`, `opencode`, `generic` | `.agents/skills/supercheck/SKILL.md` |

</Accordion>
</Accordions>

## Jobs

| Command | What it does | Key flags |
|---|---|---|
| `job list` | List jobs in the current project | `--page` (1), `--limit` (50) |
| `job get <job-id>` | Get job details | — |
| `job create` | Create a job | `--name` (required), `--tests` (required), `--description`, `--type`, `--schedule`, `--dry-run` |
| `job update <job-id>` | Update a job | `--name`, `--description`, `--schedule`, `--tests` (replaces the test list), `--dry-run` |
| `job delete <job-id>` | Delete a job with confirmation | `--force` |
| `job run` | Run a job now, bypassing the cron schedule; `--wait` exits 1 on a failed run and 5 on timeout | `--id`, `--local`, `--cloud`, `--offline`, `--playwright-config`, `--wait`, `--timeout` (300, cloud only) |
| `job trigger <job-id>` | Trigger a job with a trigger key, optionally wait | `--wait`, `--timeout` (300) |
| `job keys` | List, create and revoke trigger keys | `create --name --expires-in <seconds>` (min 60), `delete` |

```bash
supercheck job create --name "Nightly E2E" --tests <test-id> --schedule "0 2 * * *"
supercheck job run --id "Nightly E2E" --local --offline
supercheck job trigger <job-id> --wait --timeout 300
supercheck job keys <job-id>
supercheck --show-secrets job keys create <job-id> --name "CI Trigger" --expires-in 86400
supercheck job keys delete <job-id> <key-id>
```

<Accordions>
<Accordion title="Job types, status and local runs" id="supercheck-job-run">

- `job create --type` selects the runner (`playwright` or `k6`). `--tests` takes test IDs, space or comma separated.
- Job status is runtime state, not configuration. Use `job run`, `job trigger` or the dashboard to affect it.
- `job run --local --offline` runs the tests a job references in the local configuration, without credentials or server-side validation. Browser jobs use the configured Playwright browser. Pass `--playwright-config <path>` to use an existing Playwright configuration.

</Accordion>
<Accordion title="job trigger: credentials and waiting" id="supercheck-job-trigger">

`job trigger` requires `SUPERCHECK_TRIGGER_KEY`. With `--wait`, also set `SUPERCHECK_TOKEN` with access to read job details and run results in the project. A trigger key alone cannot wait for the result.

If waiting fails, resume with `supercheck run wait <run-id>`. It does not trigger another run.

</Accordion>
</Accordions>


</Callout>

## Requirements

Requirements track what the product must do and which tests prove it. `supercheck requirement` (alias `requirements`) manages them from the terminal. To manage them as code, use `requirements[]` in `supercheck.config.ts` ([Configuration](/docs/cli/configuration#requirements)).

| Command | What it does | Key flags |
|---|---|---|
| `requirement list` | List requirements with coverage status | `--search`, `--priority`, `--status` (`covered`, `failing`, `missing`), `--page` (1), `--page-size` (50, max 500) |
| `requirement get <id>` | Get a requirement with its tags, linked tests and coverage | — |
| `requirement create` | Create a requirement | `--title` (required, 1-500 characters), `--description`, `--priority`, `--tag`, `--external-id`, `--external-url`, `--test` |
| `requirement update <id>` | Update a requirement; only the flags you pass change | `create` flags, `--clear-tags`, `--clear-tests` |
| `requirement delete <id>` | Delete a requirement with confirmation | `--force` |
| `requirement link <id> <test-ids...>` | Link tests, keeping existing links (up to 100 per call) | — |
| `requirement unlink <id> <test-ids...>` | Unlink tests | — |
| `requirement coverage [id]` | Coverage for one requirement, or a count per coverage status | — |
| `requirement export` | Export requirements as CSV to stdout or a file | `--output <file>`, `--force` |

```bash
supercheck requirement create --title "Users can reset their password" --priority high --tag auth,security --test <test-id>
supercheck requirement update <requirement-id> --tag auth --clear-tests
supercheck requirement export --output requirements.csv
```

- `--tag` and `--test` repeat or take comma-separated values (up to 10 tags of 50 characters, and 100 tests). On `update` they replace the whole set. `--clear-tags` and `--clear-tests` empty it and cannot be combined with them.
- The server creates requirement tags that do not exist yet.
- `export` refuses to overwrite a file unless you pass `--force`, never writes through a symbolic link and leaves the file readable only by you. With `--json` and no `--output`, it prints `{ "format": "csv", "content": "..." }`.

<Callout type="info">
Extracting requirements from an uploaded document (PDF, DOCX, Markdown or TXT) with AI is available in the dashboard only. The CLI and MCP server do not upload documents.
</Callout>

## Monitors

| Command | What it does | Key flags |
|---|---|---|
| `monitor list` | List all monitors | `--page`, `--limit` |
| `monitor get <monitor-id>` | Get monitor details | — |
| `monitor status <monitor-id>` | Current status | — |
| `monitor results <monitor-id>` | Recent check results | `--page` (1), `--limit` (20) |

| `heartbeat ping <url>` | Send one ping from a cron job or script; no login needed | `--start`, `--fail` |

```bash
supercheck monitor create --name "API Health" --url https://api.example.com/health --type http_request --interval-minutes 5
supercheck monitor create --name "TLS port" --type port_check --url example.com --port 443
supercheck monitor create --name "Browser journey" --type synthetic_test --test-id <test-uuid>
supercheck monitor create --name "OpenAI chat" --url https://api.openai.com/v1/chat/completions --preset ai-endpoint --model gpt-4o-mini --secret OPENAI_API_KEY
supercheck monitor create --name "Docs MCP" --type mcp_server --url https://mcp.example.com/mcp --secret MCP_TOKEN --require-tool search_docs --require-tool get_page
supercheck monitor create --name "Docs MCP call" --type mcp_server --url https://mcp.example.com/mcp --call-tool search_docs --call-args '{"query":"ping"}' --expect result
supercheck monitor create --name "Nightly backup" --type heartbeat --every 1d --grace 1h
supercheck monitor update <monitor-id> --interval-minutes 1 --active false
```

<Accordions>
<Accordion title="monitor create and update flags" id="supercheck-monitor-create">

| Flag | Required | Default | Description |
|---|---|---|---|
| `--name` | Yes | — | Monitor name |
| `--url` | Except synthetic tests | — | HTTP(S) URL, or hostname/IP for ping and port checks. `mcp_server` needs an `https` URL with no credentials or fragment |
| `--type` | No | `http_request` | `http_request`, `website`, `ping_host`, `port_check`, `synthetic_test`, `heartbeat`, `mcp_server` |
| `--test-id` | Synthetic tests | — | UUID of an existing test |
| `--port` | Port checks | — | Port number (1-65535) |
| `--protocol` | No | `tcp` (`auto` for `mcp_server`) | Port check protocol (`tcp` or `udp`), or MCP protocol (`auto`, `2025`, `2026`) |
| `--interval-minutes` | No | `5` | Check interval in minutes (1–1440) |
| `--every` | Heartbeat | — | Expected ping interval: `5m`, `1h`, `1d` (1 minute to 31 days) |
| `--grace` | No | 20% of the interval, 5 min to 1 day | How late a ping may be before the monitor goes down (1 minute to 1 day). Heartbeat only |
| `--timeout` | No | `30` (`60` with the preset) | Request timeout in seconds (1-3600; 5-120 with the preset). Must not exceed `--interval-minutes` × 60 |
| `--method` | No | `GET` | `GET`, `POST`, `PUT`, `DELETE`, `PATCH`, `HEAD`, `OPTIONS`. Not allowed with `--preset` (the preset always sends `POST`) |
| `--preset` | No | — | `ai-endpoint`: check an OpenAI-compatible chat-completions endpoint (`http_request` only) |
| `--model` | With `--preset` | — | Model name to request |
| `--secret` | No | — | Name of the project secret that holds the API key (preset) or the MCP login (`mcp_server`); omit to send none. Never pass the value |
| `--key-header` | No | `Authorization` | Header for the key; `Authorization` sends `Bearer <key>`, any other header sends the raw key |
| `--prompt` | No | `Reply with the single word OK.` | Prompt to send |
| `--expect` | No | — | Text the reply must contain (case-insensitive). With `mcp_server`, text the tool call result must contain; needs `--call-tool` |
| `--max-tokens` | No | `16` | Reply token limit (1-512). Reasoning models (gpt-5, o-series) need more, for example `256` |
| `--first-token-timeout` | No | `15000` | A slower first token fails the check, in milliseconds (500-60000) |
| `--warn-first-token-ms` | No | — | Warn when the first token is slower than this for 3 checks in a row (100-60000; preset only) |
| `--warn-tokens` | No | — | Warn when a reply uses more total tokens than this (preset only) |
| `--header` | No | — | `mcp_server`: send the `--secret` value in this header instead of as a bearer token. Needs `--secret` |
| `--require-tool` | No | — | `mcp_server`: a tool the server must list. Repeat for several |
| `--call-tool` | No | — | `mcp_server`: call this tool on every check. Pick a read-only tool |
| `--call-args` | No | — | `mcp_server`: JSON object of arguments for `--call-tool` |
| `--slow-ms` | No | — | `mcp_server`: warn when a check is slower than this for 3 checks in a row (100-60000) |
| `--dry-run` | No | — | Preview what would be sent without creating |

`monitor update` accepts `--name`, `--url`, `--interval-minutes`, `--every`, `--grace`, `--timeout`, `--method`, `--active` (`true` or `false`) and `--dry-run`. Only the options you pass change, and an option that does not fit the monitor is refused. Type-specific options:

- **AI endpoint:** `--model`, `--secret`, `--key-header`, `--prompt`, `--expect`, `--max-tokens`, `--first-token-timeout`, `--warn-first-token-ms`, `--warn-tokens`.
- **MCP server:** `--secret`, `--header`, `--protocol`, `--require-tool` (replaces the list), `--call-tool` (a different tool starts with no arguments or expected text), `--call-args` (replaces the arguments; no `null` values), `--expect`, `--slow-ms`.

</Accordion>
<Accordion title="Heartbeat monitors and heartbeat ping" id="monitors-examples">

For heartbeat monitors, `monitor list` shows the state (`pending`, `up`, `late`, `down`, `paused`), the interval with its grace period and the last ping. `monitor get` and `--json` include a `heartbeat` object with `state`, `lastPingAt`, `lastPingKind`, `lastStartAt`, `nextExpectedAt` and `graceMinutes`. The ping URL is never part of these outputs.

`monitor create` prints the URL once (not with `--json` or `--quiet`). `monitor heartbeat-url` shows it again (`--quiet` prints only the URL). `--rotate` issues a new URL, the old one stops working at once, and it asks for confirmation unless you pass `--force`.

```bash
supercheck monitor heartbeat-url <monitor-id> --rotate --force
supercheck heartbeat ping "$PING_URL" --start
supercheck heartbeat ping "$PING_URL"
```

`heartbeat ping` checks that the URL path ends in `/api/heartbeat/hb_…` (an app served under a sub-path works) and sends the ping (`/start` with `--start`, `/fail` with `--fail`) with a 10-second timeout per request.

- It retries `429`, `503`, network errors and timeouts up to 3 times. It waits as long as the server's `Retry-After` asks (at most 30 seconds) or else 1, 2 and 4 seconds, and gives up within about 60 seconds. Other HTTP errors are not retried.
- Exit codes: `0` on a 2xx answer, `4` on another HTTP status, `5` on timeout, `1` when it cannot connect.
- The endpoint answers `200` even for an unknown or rotated URL, so check that the monitor turns **Up**. See [Heartbeat monitors](/docs/app/heartbeat).

</Accordion>
</Accordions>

## Notification providers

`notifications` is an alias for `notification`.

| Command | What it does | Key flags |
|---|---|---|
| `notification list` | List providers, with each channel's health (`ok`, `auth_failed`, `failing`, `unknown`) from its latest delivery in the past 7 days | — |
| `notification get <id>` | Get provider details | — |
| `notification create` | Create a provider | `--type`, `--name` (both required), `--payload`, `--routing-key-stdin` (PagerDuty) |
| `notification update <id>` | Update a provider | `--name`, `--type`, `--payload`, `--routing-key-stdin` (PagerDuty) |
| `notification delete <id>` | Delete a provider | `--force` |
| `notification test <id>` | Send a test through a saved channel; webhooks and paging services get a test page with dedup key `test:<id>` and the receiver's HTTP status | `--resolve` (close the test page) |
| `notification test` | Test an unsaved configuration | `--type`, `--payload` (one payload option required) |

Types: `email`, `slack`, `webhook`, `telegram`, `discord`, `teams`, `pagerduty`. `--payload` is a JSON object; `--data` and `--config` are aliases. `--type pagerduty` creates a PagerDuty Events API v2 channel (a webhook with the `pagerduty` preset, as in the app) and takes no `--payload`. Give it the integration's routing key in the `PAGERDUTY_ROUTING_KEY` environment variable, or pipe it in with `--routing-key-stdin`. The key is never accepted as an argument and is masked in output (`--show-secrets` prints it). `notification update <id> --type pagerduty` replaces the saved key the same way, which rotates it. `notification list` shows the preset, so a PagerDuty channel reads `webhook` / `pagerduty`. The other paging presets are set up in the app; the CLI can list and test those channels.

```bash
supercheck notification create --type slack --name "Slack Alerts" \
  --payload '{"webhookUrl":"https://hooks.slack.com/..."}'
supercheck notification create --type pagerduty --name "On call" --routing-key-stdin < routing-key.txt
supercheck notification test <id> --resolve
```

<Accordions>
<Accordion title="Updating providers with secret fields" id="supercheck-notification-update">

- `--payload` on update replaces the entire config, so include all fields. The CLI never merges your input with masked values from the server. Without a payload, only `--name` and `--type` change and existing secrets are kept.
- `pull` leaves a body template that holds a credential, such as a PagerDuty routing key, out of `supercheck.config.ts` and says so. A `deploy` that updates the provider keeps the saved key. To create that provider in another project, set `PAGERDUTY_ROUTING_KEY` for the deploy, which fills the template of a `preset: 'pagerduty'` provider being created. To change a saved key, run `notification update <id> --type pagerduty`.
- `notification test` without an id needs exactly one of `--payload`, `--data` or `--config`. With an id, the saved configuration is used and payload options are rejected.
- A test the receiver rejects exits with a general error and prints the result, for example `Authentication rejected (HTTP 401). Check the integration key.` for a bad key.

### Incidents

```bash
supercheck incident list --status investigating --severity sev1
supercheck incident list --assignee me
supercheck incident resolve <incident-number-or-uuid> --summary "Traffic restored after rollback"
supercheck incident create --title "Checkout errors reported by customers" --severity sev2 \
  --service "Checkout API" --monitor <monitor-uuid> --summary "Support reports 500s at payment"
supercheck incident resources <incident-number-or-uuid> --add-service "Checkout API" --remove-monitor <monitor-uuid>
supercheck incident create --title "Login outage" --severity sev1 \
  --status-page <status-page-uuid> --component <component-uuid> --impact major --message "We are investigating." --notify
```

`incident create` opens an incident with the same notifications and reminders as one opened by an alert.

- Only `--title` is required. `--severity` defaults to `sev3`.
- `--service` takes a UUID or the exact service name, and that service's owner becomes the assignee.
- Each `--monitor` and `--affected-service` is listed as affected: its next alert joins this incident instead of opening a new one.
- `--commander` takes `me` or a user UUID.
- `--status-page` with at least one `--component` also posts a public incident. Subscribers are emailed only with `--notify`. If the public post fails, the incident is still created and the command warns.
- Declaring needs editor access or above. Rate limits are in [Incidents](/docs/app/investigate/incidents).

The **Status** column shows the display label (Triggered, Acknowledged, Investigating, Fixing, Monitoring, Resolved), also returned as `statusLabel` with `--json`. `--status` filters on stored values: `open` (every incident that is not resolved), `triggered`, `investigating`, `identified`, `recommendations_ready`, `user_applying_fix`, `verifying`, `resolved`.

Resolving prompts for confirmation and stores the summary in the incident timeline and audit log. Use `--force` only in reviewed automation.

```bash
supercheck incident policy set --first-reminder 15 --repeat 60 --max 3
supercheck incident policy set --escalate-after 30 --escalate-member <user-id>
supercheck incident policy set --first-reminder off --escalate-after off
```

`incident policy set` needs project update permission. Minutes are 5 to 1,440 and the reminder schedule must finish within two days. Turning reminders off also clears the repeat. Turning escalation off clears its target. The escalation channel cannot be a paging service. See [Default policy](/docs/app/investigate/incidents).

### Maintenance windows

During a window monitors keep running, but alerts, incidents and reminders are muted and uptime leaves it out. See [Maintenance windows](/docs/app/monitor#maintenance-windows).

| Command | What it does | Key flags |
|---|---|---|
| `maintenance list` | List windows | `--state active\|scheduled\|past`, `--monitor <id>`, `--service <id>` |
| `maintenance get <id>` | Show one window | — |
| `maintenance create` | Schedule a window | `--title`, `--start "YYYY-MM-DD HH:MM"`, `--duration` (required); scope `--project`, `--service`, `--monitor` (pick one, repeatable); `--description`, `--timezone`, `--repeat daily\|weekly\|monthly`, `--days mon,thu`, `--day 1-28\|last`, `--until YYYY-MM-DD`, `--status-page` + `--component`, `--notify` |
| `maintenance update <id>` | Change a window; only the flags you pass change | `--title`, `--description`, a scope flag, `--start`, `--duration`, `--timezone`, `--repeat once\|daily\|weekly\|monthly`, `--days`, `--day`, `--until YYYY-MM-DD\|none` |
| `maintenance end <id>` | End an active window now | — |
| `maintenance extend <id>` | Extend an active window (never shortens it) | exactly one of `--by 30m` or `--to <ISO 8601 date-time>`; no offset means local time |
| `maintenance cancel <id>` | Cancel a scheduled window, or the rest of a recurring one | — |
| `maintenance delete <id>` | Delete a window that is not active | `--force` |

`--start` is the local start in `--timezone` (default: your machine's zone). On `update`, `--start` without `--timezone` uses the window's zone. A one-off window can show on a status page with `--status-page <id> --component <id>`, set at create only.

```bash
supercheck maintenance create --title "DB upgrade" --monitor <monitor-uuid> \
  --start "2026-11-20 02:00" --duration 90m --timezone Europe/Berlin
supercheck maintenance extend <window-uuid> --to 2026-11-20T04:00:00Z
```

## Monitoring-as-Code

| Command | What it does | Key flags |
|---|---|---|
| `pull` | Pull remote resources into local config and files | `--dry-run`, `--force`, `--tests-only`, `--config-only`, `--skip-install` (skip dependency install when initializing a project) |
| `diff` | Preview changes between local config and server state | `--delete` |
| `deploy` | Push configuration to the API | `--dry-run`, `--delete`, `--no-delete`, `--force`, `--verify`, `--verify-timeout <seconds>` |
| `destroy` | Tear down all managed resources defined with IDs in the local config, including notification providers, requirements and status pages | `--dry-run`, `--force` |

```bash
supercheck pull --dry-run
supercheck diff
supercheck deploy --dry-run
supercheck deploy --force --verify   # then run each created or updated browser test once in the cloud
supercheck destroy --dry-run
```

<Callout type="warn">
`supercheck destroy` needs `--force` to confirm deletion or `--dry-run` to preview. Bare `supercheck destroy` errors.
</Callout>

`diff` and `deploy` keep remote resources that are absent from config. Use `diff --delete` to preview pruning, then `deploy --delete` to apply it. Pruning includes resources created outside this config, and removes components absent from a declared list. `--force` skips the confirmation prompt. Keep test scripts as editable source files and review `supercheck diff` before deploying.

<Accordions>
<Accordion title="supercheck pull: files, backups and overwrites" id="supercheck-pull">

Config pulls include monitors (with tags), jobs, requirements, notification providers, variables, tags and status pages (settings, branding, notifications and components). Test pulls also write scripts under `_supercheck_/` with `@title`, `@priority` and `@tags` annotations, plus `@type` for agent, API, database and custom tests. Pull preserves managed test paths and existing browser and `testMatch` settings. Runner-type changes migrate files with backups. New tests must match configured custom globs or pull stops before writing.

When pull overwrites changed files it saves a mode-`0600` backup at `<path>.supercheck-backup.<uuid>`. This covers test scripts and config files, and a test file renamed during pull is backed up before removal. Backups are kept until you delete them. When a pull creates backups it adds the backup pattern to an existing `.gitignore` (it never creates one) and prints a one-line note.

In JSON mode the summary includes `files` and `backups` arrays with the paths written and preserved. `--dry-run` writes no files and creates no backups.

</Accordion>
<Accordion title="supercheck diff" id="supercheck-diff">

Includes requirements and status pages. Notification provider changes include nested `config` fields such as webhook `bodyTemplate`.

</Accordion>
<Accordion title="supercheck deploy: renames and --verify" id="supercheck-deploy">

Deploy pushes notification provider config and webhook body templates too. Renaming an ID-less non-test resource creates a separate resource, and the old remote one stays unless you use `--delete`. Carry its explicit ID or pull it first to update the existing resource.

`--verify` runs every browser test this deploy created or updated once and waits for the result (up to 5 tests, `--verify-timeout <seconds>` each). k6 tests are deployed but never run implicitly because they use load budget. Run them with `supercheck test execute` after you approve the target, load and spend. If a verification run fails, the command exits `1` and the error lists each failed test with its run ID (also in `--json` under `verification`).

</Accordion>
<Accordion title="supercheck deploy: requirements, status pages and tags" id="supercheck-deploy-resources">

- **Requirements:** compared and pruned only when the config has a `requirements` key. Omitted `tags` or `tests` leave the remote value alone and `[]` clears it. Tag names compare case-insensitively.
- **Status pages:** `subdomain` is read-only (pulled, never sent). Notification flags you omit stay unchanged. When the page declares `components`, remote-only components are removed only with `--delete`. Omitting `components` leaves them all alone.
- **Tests:** `@priority` and `@tags` annotations are applied on deploy.
- **Tags:** test and monitor `tags` must already exist in the project or be declared under `tags` in the config. Deploy checks this before any write, matching names case-insensitively. The server creates requirement tags.

</Accordion>
</Accordions>
