## Global Flags

Available on all commands, before or after the subcommand:

```bash
supercheck --json job trigger <job-id> --wait
supercheck --quiet whoami
supercheck config validate --json
```

| Flag | Description |
|---|---|
| `--json` | Output in JSON format (for CI/CD scripting) |
| `--envelope` | Include pagination metadata with JSON list results; requires `--json` |
| `--show-secrets` | Disable redaction for sensitive fields in command output |
| `--quiet` | Suppress non-essential output (only IDs and errors) |
| `--wide` | Show tables without width limits |
| `--no-color` | Disable ANSI colors |
| `--debug` | Enable debug logging |
| `-v`, `--version` | Show version |

Config-aware commands (for example `config`, `diff`, `deploy`, `pull`, `validate`, `destroy`) also accept `--config <path>` to point at a specific config file.

<Accordions>
<Accordion title="JSON output and secret redaction" id="json-output">

- For `sre ask`, `sre brief`, `run stream`, and `test status`, global `--json` produces newline-delimited JSON (NDJSON), one event per line.
- List commands keep their existing JSON array shape for compatibility. Add `--envelope` to include pagination metadata.
- Local test and job runs emit bounded NDJSON `local.result` records in JSON mode.
- Errors are emitted on stderr. With `--json`, fatal errors are JSON on stderr with `error`, `exitCode`, and API `status` and `details` when available.
- Sensitive fields are redacted by default, including notification provider webhook URLs, Discord and Teams webhook credentials, and provider config headers (monitor target URLs stay visible and credential headers are masked). Use `--show-secrets` only when the output can be handled securely.
- Creating a trigger key requires `--show-secrets` to display its one-time plaintext value. The command fails before making the request when the flag is absent.

</Accordion>
<Accordion title="Terminal output details" id="investigation-status-and-terminal-output">

Use `--wide` for unrestricted table values or `--json` for complete structured payloads. `--no-color` and `NO_COLOR` disable colors. Pipes have no colors or spinners. Interactive stream connections show elapsed waiting time; GET streams retry one failed initial connection. Writes and POST streams are not replayed. Ctrl+C exits 130; stream idle timeouts exit 5.

`config print` uses indented JSON in human mode, with secret variable values masked. Test create/update summaries omit the script blob; use `test get <id> --include-script` to read decoded source.

Structured SRE output follows the same Field/Value detail-table format as monitors, tests, and jobs. Triage separates run metadata from the complete narrative summary. Copilot answers and evidence briefs have report headings; quiet mode suppresses their content. Quiet detail output resolves IDs from API envelopes, and `--json` takes precedence when combined with `--quiet`.

</Accordion>
</Accordions>

## Exit Codes

| Code | Meaning | Example |
|---|---|---|
| `0` | Success | Job completed successfully |
| `1` | General error | Test failed, monitor down |
| `2` | Authentication error | Invalid token, expired token |
| `3` | Configuration error | Missing config, invalid schema |
| `4` | Network / API error | API unreachable, 5xx response |
| `5` | Timeout | Operation exceeded timeout |
| `130` | Interrupted | Ctrl+C during a stream |

An operation that requires confirmation exits `3` when declined or when input closes (`ABORTED`), and exits `3` with `CONFIRMATION_REQUIRED` when confirmation is unavailable in a non-interactive session. Review its plan, then pass `--force` to apply the already-authorized change. Authentication errors continue to use exit code `2`.

## Agent-first operation

| Command | What it does | Key flags |
|---|---|---|
| `supercheck skills [topic]` | Print the offline workflow index or a focused guide (`local`, `sync`, `configure`, `execute`, `investigate`). Bundled with the CLI version; no credentials | — |
| `supercheck skills install` | Write a small `.agents/skills/supercheck/SKILL.md` pointer. Existing skill files are preserved unless `--force` | `--path <directory>`, `--force` |
| `supercheck capabilities` | Report CLI version, local workflow capabilities, and whether credentials are present | `--online` |
| `supercheck schema config` | Describe the installed configuration schema without loading repository code | `--json` |

```bash
supercheck skills
supercheck skills local
supercheck skills sync
supercheck skills configure
supercheck skills execute
supercheck skills investigate
supercheck capabilities --json
supercheck capabilities --online --json
supercheck schema config --json
```

`--online` verifies the current API context with one request; it does not prove every server feature is available or that the token has permission for every operation. Diagnostic commands tolerate an invalid project config: an explicit, environment, or stored URL identifies the target and skips config loading. Otherwise a valid config supplies its API URL; if config loading fails, diagnostics warn in human-readable output and fall back to the default API URL.

### Machine-readable plans and writes

`diff --json` and `deploy --dry-run --json` return plans on stdout. Successful deploys return per-resource results, including server-assigned IDs and the state-file path. `pull --dry-run --json` describes the remote resources and config path it would write. Other mutation `--dry-run --json` commands return the proposed request payload.

JSON errors on stderr carry a stable `code` agents can branch on, with `retryable` and suggested `nextActions` where useful. Existing `error` strings and exit codes are unchanged.

| Code | Meaning |
|---|---|
| `AUTH_REQUIRED` | No credential; run `supercheck login` |
| `TOKEN_INVALID` | Credential expired, revoked or rejected; run `supercheck login --reauth` |
| `PERMISSION_DENIED` | Authenticated but not allowed (role or project) |
| `SUBSCRIPTION_REQUIRED` | No active plan; a person must choose one in the dashboard |
| `SPENDING_LIMIT_REACHED` | The organization's spending limit blocks execution |
| `RATE_LIMITED` / `SERVICE_UNAVAILABLE` | Retryable |
| `VALIDATION_FAILED` | The request was rejected as invalid |
| `CONFIRMATION_REQUIRED` | A write needs `--force` |
| `PAYMENT_REQUIRED` | The server answered 402 without a recognised reason; run `supercheck plan` |
| `AUTHORIZATION_PENDING` | `login` without `--json` or a terminal started a browser login that is not approved yet (exit `2`); approve it, then run `login` again |
| `DEVICE_CODE_DENIED`, `DEVICE_CODE_EXPIRED`, `DEVICE_CODE_CONSUMED`, `DEVICE_LOGIN_UNVERIFIED`, `TOKEN_LIMIT_REACHED` | Browser-login outcomes |
| `CONTEXT_MISMATCH` | The config's API URL, organization or project does not match the logged-in context; see `supercheck link` |

In a non-interactive session, a write requiring confirmation refuses with exit code `3` and a `CONFIRMATION_REQUIRED` error. Review the preview before explicitly passing `--force`. The CLI checks that config organization/project match the authenticated API context before sync operations.

<Callout type="info">
Deploy records returned IDs in `supercheck.state.json`, keyed by API origin and actual organization/project. Share this generated mapping with CI so subsequent deploys manage the same resources. The transient `.lock` coordinates deploys only on a shared local filesystem; do not commit it. Names alone do not establish ownership; pull an existing resource or set its explicit ID. Deploy does not rename local test files.
</Callout>

## Authentication

| Command | What it does | Key flags |
|---|---|---|
| `supercheck login` | Sign in through your browser, or store a CLI token | `--token`, `--url`, `--reauth`, `--no-browser`, `--wait`, `--timeout` |
| `supercheck link` | Point `supercheck.config.ts` at the org and project you are logged in to | `--dry-run`, `--force` |
| `supercheck onboard` | Read-only status of the current directory and the single next command | — |
| `supercheck discover` | Bounded, read-only facts about the repository | `--root <directory>` |
| `supercheck plan` | Show whether the organization has an active subscription | — |
| `supercheck ci init --github` | Write `.github/workflows/supercheck.yml` | `--path <file>`, `--force` |
| `supercheck agent install` | Install the Supercheck skill for a coding agent | `--target`, `--path`, `--pointer`, `--force` |
| `supercheck whoami` | Show the authenticated project, organization and role | — |
| `supercheck logout` | Clear stored credentials | — |

```bash
supercheck login
supercheck login --token <token>
supercheck whoami
supercheck logout
```

`whoami` includes token identity and expiry when your role permits viewing API keys (user, token name, API URL, expiry); read-only users can still verify their context.

<Accordions>
<Accordion title="supercheck login: flags and browser sign-in" id="supercheck-login">

```bash
supercheck login --token <token>
supercheck login --token <token> --url https://supercheck.yourdomain.com
```

| Flag | Description |
|---|---|
| `--token <token>` | CLI token (`sck_live_*` or `sck_test_*`). Without it, the CLI signs in through your browser when the server supports it |
| `--url <url>` | API base URL; otherwise uses `SUPERCHECK_URL`, stored URL, config URL, then the cloud default |
| `--reauth` | Start a new browser login even if you are already signed in |
| `--no-browser` | Print the login URL and code without opening a browser |
| `--wait` | Wait for browser approval instead of returning immediately (default in an interactive terminal) |
| `--timeout <seconds>` | With `--wait`: give up after this long (30 to 3600, default 900); the login stays resumable. A dropped connection during the wait is retried until then |

A token is verified against the API before being stored locally.

**Browser login.** `supercheck login` starts a device-authorization sign-in: it prints a URL and a short code, you approve the request in the browser (choosing the project the CLI may access), and the CLI stores a project-scoped key that expires in 90 days. Only approve a code you just requested yourself. Enter the code from your terminal in the confirmation field; the info icon shows the request code and requester address for comparison.

- **Interactive terminal:** the command waits for approval and opens your browser. Use `--no-browser` to print the URL only.
- **Agents and scripts:** `supercheck login --json` prints the URL and code and **returns immediately** with `"state": "authorization_pending"`. Run the same command again after approval to finish. With `--wait` it blocks instead: it prints the pending object first (so the URL and code can be shown), then a second JSON line with the result.
- **Re-authenticating:** `--reauth` starts a new login even if you are already signed in. `SUPERCHECK_TOKEN`, if set, always takes precedence over a stored login.
- **Plans:** if the organization you pick has neither an active trial nor a paid plan (cloud only), the approval page says so and, if you own the organization, offers **Choose a plan**. That makes the organization active and opens billing in a new tab, so the right organization is charged and your login code stays valid. Approving never depends on a plan: you can connect and run tests locally first. Cloud runs require an active trial or plan, as shown beside the approval controls. Run `supercheck plan` afterwards to confirm.
- **Self-hosted:** if the server does not enable browser login, the command explains how to use `--token`. Point at your instance with `--url` or `SUPERCHECK_URL`.

</Accordion>
<Accordion title="supercheck link" id="supercheck-link">

Points `supercheck.config.ts` at the organization and project you are logged in to. It edits only the `organization` and `project` values and the default API URL written by `supercheck init`, treating the file as text (it is never executed) and writing values as quoted strings. Identifiers returned by the server must be plain identifiers or nothing is written. If the config already targets a different project it refuses with `CONTEXT_MISMATCH`; `--dry-run` shows that conflict without failing, and `--force` replaces the existing values, so use it only after confirming the change.

</Accordion>
<Accordion title="supercheck onboard, discover and plan" id="supercheck-onboard">

**`onboard`** is read-only. It reports the state (`needs_init`, `needs_tests`, `needs_auth`, `needs_link`, `needs_plan`, `ready_to_deploy`, `deployed`) and the single next command. It never changes files or the cloud and is safe to run repeatedly.

**`discover`** prints bounded, read-only facts about the repository: package manager, framework, routes, existing Playwright and k6 tests, CI provider and the key names (never values) from `.env.example`. It does not run scripts, import configuration, read `.env`, or follow symlinks.

**`plan`** shows whether the organization has an active subscription. An unknown result is never treated as free or paid; the server enforces limits on every request.

</Accordion>
<Accordion title="supercheck ci init and agent install" id="supercheck-ci-init---github">

**`ci init --github`** writes `.github/workflows/supercheck.yml`: pull requests run tests locally without credentials, and pushes to `main` deploy using the `SUPERCHECK_TOKEN` repository secret. It does not create that secret. It refuses to overwrite an existing file without `--force`.

**`agent install`** installs the Supercheck skill for a coding agent with `--target claude`, `cursor`, `codex`, `opencode` or `generic`. Existing files are never overwritten without `--force`; `--pointer AGENTS.md` adds a short block delimited by markers and only ever rewrites that block.

</Accordion>
</Accordions>

## Configuration

| Command | What it does | Key flags |
|---|---|---|
| `supercheck init` | Create `supercheck.config.ts` and the `_supercheck_/` folder | `--force`, `--skip-install`, `--skip-examples`, `--pm <manager>` |
| `supercheck config validate` | Validate the configuration file schema | `--offline` |
| `supercheck validate` | Validate local test scripts using the same rules as Playground | — |
| `supercheck config print` | Print the resolved configuration with environment variable expansion | `--offline` |

```bash
supercheck init
supercheck init --force              # Overwrite existing config
supercheck init --skip-install       # Skip dependency installation
supercheck init --skip-examples      # Skip example test files
supercheck init --pm pnpm            # Use specific package manager (npm, pnpm, yarn, bun)
supercheck config validate
supercheck config validate --offline
supercheck validate
supercheck config print
supercheck config print --offline
```

`--offline` validates or prints a local-only config without API credentials. Both modes require an existing config file; `--offline` skips cloud project identity checks. `config print` redacts sensitive provider values, including webhook URLs and config headers; monitor URLs remain visible and credential headers are masked.

## Jobs

| Command | What it does | Key flags |
|---|---|---|
| `job list` | List jobs in the current project | `--page` (1), `--limit` (50) |
| `job get <job-id>` | Get job details | — |
| `job create` | Create a job | `--name` (required), `--tests` (required), `--description`, `--type`, `--schedule`, `--dry-run` |
| `job update <job-id>` | Update job configuration | `--name`, `--description`, `--schedule`, `--dry-run` |
| `job delete <job-id>` | Delete a job with confirmation | `--force` |
| `job run` | Run a job immediately, bypassing the cron schedule | `--id`, `--local`, `--cloud`, `--offline`, `--playwright-config` |
| `job trigger <job-id>` | Trigger a job with a trigger key, optionally wait | `--wait`, `--timeout` (300) |
| `job keys` | List, create and revoke trigger keys | `create --name --expires-in`, `delete` |

```bash
supercheck job list --page 2 --limit 10
supercheck job create --name "Nightly E2E" --tests <test-id> --schedule "0 2 * * *"
supercheck job create --name "Smoke Tests" --tests id1,id2 --type k6 --dry-run
supercheck job update <job-id> --schedule "0 3 * * *" --dry-run
supercheck job delete <job-id> --force

supercheck job run --id <job-id>
supercheck job run --id <job-id> --local     # Run locally
supercheck job run --id <job-id> --cloud     # Run in the cloud
supercheck job run --id "Nightly E2E" --local --offline

supercheck job trigger <job-id>
supercheck job trigger <job-id> --wait --timeout 300
supercheck --json job trigger <job-id> --wait

supercheck job keys <job-id>
supercheck --show-secrets job keys create <job-id> --name "CI Trigger"
supercheck --show-secrets job keys create <job-id> --name "Temp Key" --expires-in 86400
supercheck job keys delete <job-id> <key-id>
```

<Accordions>
<Accordion title="Job types, status and local runs" id="supercheck-job-run">

- `job create --type` selects the runner (`playwright` or `k6`). `--tests` takes test IDs (space or comma separated). Test `--type` uses API types: `browser`, `performance`, `api`, `database`, `custom`.
- Job status is runtime state, not configuration. Use `job run`, `job trigger`, or the dashboard/scheduler to affect execution state.
- `job run --local --offline` runs tests referenced by a job in the local configuration without credentials or server-side validation. Browser jobs use the configured Playwright browser. Pass `--playwright-config <path>` to use an existing Playwright configuration.

</Accordion>
<Accordion title="job trigger: credentials and waiting" id="supercheck-job-trigger">

`job trigger` requires `SUPERCHECK_TRIGGER_KEY`. If you also use `--wait`, set `SUPERCHECK_TOKEN` with access to read job details and run results in the project. The CLI reads the job before triggering, then polls the accepted run; a trigger key alone cannot wait for the result.

The CLI validates the read token and job before starting a waited trigger. If waiting later fails, use the returned run ID with `supercheck run wait <run-id>` to resume observation without triggering another run.

</Accordion>
</Accordions>

## Runs

| Command | What it does | Key flags |
|---|---|---|
| `run list` | List job runs. Runs of a test executed directly (`test execute`) are not listed; follow those with `run get <runId>` or `--wait` | `--page`, `--limit`, `--job <job-id>`, `--status` (`queued`, `running`, `passed`, `failed`, `error`, `blocked`) |
| `run get <run-id>` | Get run details | — |
| `run permissions <run-id>` | Get run access permissions | — |
| `run status <run-id>` | Quick status check | — |
| `run wait <run-id>` | Wait for an existing run to reach a terminal state; never starts or retriggers a run | `--timeout <seconds>` (300) |
| `run stream <run-id>` | Watch live console output | `--idle-timeout` (60, min 10) |
| `run cancel <run-id>` | Cancel a running execution | — |
| `run delete <run-id>` | Delete a run and its stored artifacts (active runs are refused) | `--force` (skip confirmation) |
| `dashboard` | Show project dashboard metrics (monitors, jobs, runs, queue) | — |

```bash
supercheck run list --job <job-id> --status failed --limit 20
supercheck run get <run-id>
supercheck run wait <run-id> --timeout 600
supercheck run stream <run-id> --idle-timeout 120
supercheck run cancel <run-id>
supercheck run delete <run-id> --force
supercheck dashboard --json
```

`run stream`: failed, cancelled, blocked, or missing runs return a nonzero exit code. Ctrl-C cancels the client stream; `--json` emits NDJSON events. `--idle-timeout` is the number of seconds to wait with no data before timing out.

supercheck test run --all --type performance
supercheck test run --offline --file ./_supercheck_/playwright/homepage.pw.ts
supercheck test run --all --offline --playwright-config ./playwright.config.ts

supercheck test execute <test-id>

supercheck test execute <test-id> --location us-east --wait
supercheck test status <test-id> --idle-timeout 120

</Callout>

## Requirements

Requirements track what the product must do and which tests prove it. `supercheck requirement` (alias `requirements`) manages them from the terminal; you can also manage them as code with `requirements[]` in `supercheck.config.ts` (see [Configuration](/docs/cli/configuration#requirements)). They need a server version that includes the requirements REST API.

| Command | What it does | Key flags |
|---|---|---|
| `requirement list` | List requirements with coverage status | `--search`, `--priority`, `--status` (`covered`, `failing`, `missing`), `--page` (1), `--page-size` (50) |
| `requirement get <id>` | Get a requirement with its tags, linked tests and coverage | — |
| `requirement create` | Create a requirement | `--title` (required, 1-500 characters), `--description`, `--priority`, `--tag`, `--external-id`, `--external-url`, `--test` |
| `requirement update <id>` | Update a requirement; only the flags you pass change | `create` flags, `--clear-tags`, `--clear-tests` |
| `requirement delete <id>` | Delete a requirement with confirmation | `--force` |
| `requirement link <id> <test-ids...>` | Link tests, keeping existing links (up to 100 per call) | — |
| `requirement unlink <id> <test-ids...>` | Unlink tests | — |
| `requirement coverage [id]` | Coverage for one requirement, or a count per coverage status | — |
| `requirement export` | Export requirements as CSV to stdout or a file | `--output <file>`, `--force` |

```bash
supercheck requirement list --priority high --status failing
supercheck requirement get <requirement-id>
supercheck requirement create --title "Users can reset their password" --priority high --tag auth,security --test <test-id>
supercheck requirement update <requirement-id> --priority medium
supercheck requirement update <requirement-id> --tag auth --clear-tests
supercheck requirement link <requirement-id> <test-id-1> <test-id-2>
supercheck requirement unlink <requirement-id> <test-id-1>
supercheck requirement coverage
supercheck requirement export --output requirements.csv
supercheck requirement delete <requirement-id> --force
```

`--tag` and `--test` repeat or take comma-separated values (up to 10 tags of 50 characters, and 100 tests). On `update` they replace the whole set; `--clear-tags` and `--clear-tests` empty it and cannot be combined with them. Requirement tags that do not exist yet are created by the server. `export` refuses to overwrite a file unless you pass `--force`, never writes through a symbolic link, and leaves the file readable only by you. With `--json` and no `--output`, it prints `{ "format": "csv", "content": "..." }`.

<Callout type="info">
Extracting requirements from an uploaded document (PDF, DOCX, Markdown or TXT) with AI is available in the dashboard only. The CLI and MCP server do not upload documents.
</Callout>

## Monitors

| Command | What it does | Key flags |
|---|---|---|
| `monitor list` | List all monitors | `--page`, `--limit` |
| `monitor get <monitor-id>` | Get monitor details | — |
| `monitor status <monitor-id>` | Current status (quick view) | — |
| `monitor results <monitor-id>` | Recent check results | `--page` (1), `--limit` (20) |
| `monitor stats <monitor-id>` | Performance statistics | — |
| `monitor create` | Create a monitor | `--name` (required), `--url`, `--type`, `--test-id`, `--port`, `--protocol`, `--interval-minutes`, `--timeout`, `--method`, `--dry-run` |
| `monitor update <monitor-id>` | Update a monitor | `--name`, `--url`, `--interval-minutes`, `--timeout`, `--method`, `--active`, `--dry-run` |

```bash
supercheck monitor list --page 2 --limit 10
supercheck monitor results <monitor-id> --page 2 --limit 20

supercheck monitor create --name "API Health" --url https://api.example.com/health --type http_request --interval-minutes 5
supercheck monitor create --name "Website" --url https://example.com --dry-run
supercheck monitor create --name "TLS port" --type port_check --url example.com --port 443
supercheck monitor create --name "Browser journey" --type synthetic_test --test-id <test-uuid>

supercheck monitor update <monitor-id> --interval-minutes 1 --active false
supercheck monitor update <monitor-id> --name "Updated" --method POST --dry-run
supercheck monitor delete <monitor-id> --force
```

<Accordions>
<Accordion title="monitor create and update flags" id="supercheck-monitor-create">

| Flag | Required | Default | Description |
|---|---|---|---|
| `--name` | Yes | — | Monitor name |
| `--url` | Except synthetic tests | — | HTTP(S) URL, or hostname/IP for ping and port checks |

## AI SRE

AI SRE commands use the active project from the CLI token and preserve the same tenant and RBAC boundaries as the dashboard. Plural aliases `incidents` and `services` are also supported.

| Command | What it does | Key flags |
|---|---|---|
| `incident list` | List incidents (assignee and acknowledgement shown) | `--status`, `--severity`, `--assignee me\|unassigned\|<user-id>` |
| `incident get <ref>` | Get an incident | — |
| `incident timeline <ref>` | Incident timeline | — |
| `incident assign <ref>` | Assign the incident, or its commander, to a project editor or admin | `--user <user-id\|me>` (required), `--commander` |
| `incident unassign <ref>` | Clear the assignee (or commander) | `--commander` |
| `incident ack <ref>` | Acknowledge an incident | — |
| `incident resolve <ref>` | Resolve with a required summary | `--summary` (`--comment` is an alias), `--force` |
| `sre triage <ref>` | Classify an incident | — |
| `sre investigate <ref>` | Start an asynchronous deep investigation | `--live-connectors` |
| `sre brief <ref>` | Stream an evidence brief | `--idle-timeout` |
| `sre ask "<question>"` | Ask Copilot (read-only) | `--incident <ref>`, `--live-connectors`, `--idle-timeout` |
| `sre status <runId>` | Follow a triage or accepted investigation | — |
| `service list/get/health/dependencies` | Read-only service catalog | needs `sre_service:view` |

`<ref>` is the number shown by `incident list` or a UUID. Numbers resolve within the CLI token's project; they are not row positions. Use `incident list --json` to see UUIDs. Manual triage and investigations are enabled by default with a configured AI provider; existing operator opt-outs remain effective (`503 feature_disabled` identifies the setting to change, and you recreate containers after changing `.env`). Automatic AI work remains opt-in.

### Incidents

```bash
supercheck incident list --status investigating --severity sev1
supercheck incident list --status open   # every incident that is not resolved
supercheck incident get <incident-number-or-uuid>
supercheck incident timeline <incident-number-or-uuid>
supercheck incident list --assignee me
supercheck incident assign <incident-number-or-uuid> --user me
supercheck incident ack <incident-number-or-uuid>
supercheck incident resolve <incident-number-or-uuid> --summary "Traffic restored after rollback"
```

Resolution prompts for confirmation and stores the required summary in the incident timeline and audit log. Use `--force` only in reviewed automation.

### Triage and investigation

```bash
supercheck sre triage <incident-number-or-uuid>
supercheck sre investigate <incident-number-or-uuid>
supercheck sre investigate <incident-number-or-uuid> --live-connectors
supercheck sre brief <incident-number-or-uuid>
supercheck sre brief <incident-number-or-uuid> --idle-timeout 120
supercheck sre status <runId>
```

Deep investigation is asynchronous: a successful command returns an accepted investigation-run ID. Follow progress with `incident get` and `incident timeline`, or `sre status <runId>` (requires a matching app release with the investigation-status endpoint). `--live-connectors` enables configured read-only telemetry tools only when the caller also has `sre_connector:investigate` permission.

### Copilot

```bash
supercheck sre ask "Why did checkout latency increase?"
supercheck sre ask "Summarize the strongest evidence" --incident <incident-number-or-uuid>
supercheck sre ask "Check current telemetry" --incident <incident-number-or-uuid> --live-connectors
```

Copilot is read-only. Use an incident your token can access, and add `--live-connectors` only when you have connector investigation permission. `--idle-timeout` controls stream inactivity (minimum 10 seconds). Ctrl-C cancels the client stream. Global `--json` emits NDJSON events for automation. Streamed errors and AI-provider unavailability return a nonzero exit code for both Copilot and evidence briefs.

### Service catalog

```bash
supercheck service list
supercheck service get <service-id>
supercheck service health <service-id>
supercheck service dependencies <service-id>
```

These commands are read-only and require `sre_service:view`.

## Monitoring-as-Code

| Command | What it does | Key flags |
|---|---|---|
| `pull` | Pull remote resources into local config and files | `--dry-run`, `--force`, `--tests-only`, `--config-only` |
| `diff` | Preview changes between local config and server state | `--delete`, `--no-delete` |
| `deploy` | Push configuration to the API | `--dry-run`, `--delete`, `--no-delete`, `--force`, `--verify`, `--verify-timeout <seconds>` |
| `destroy` | Tear down all managed resources defined with IDs in the local config, including notification providers, requirements and status pages | `--dry-run`, `--force` |

```bash
supercheck pull
supercheck pull --dry-run
supercheck pull --force
supercheck pull --tests-only
supercheck pull --config-only

supercheck diff

supercheck deploy
supercheck deploy --dry-run      # Preview without applying
supercheck deploy --delete       # Delete remote resources absent from config (and components absent from a declared list)
supercheck deploy --force        # Skip confirmation
supercheck deploy --force --verify   # Then run each created/updated browser test once in the cloud

supercheck destroy --dry-run      # Preview resources to be deleted
supercheck destroy --force        # Confirm and delete resources
```

<Callout type="warn">
`supercheck destroy` requires `--force` to confirm deletion, or `--dry-run` to preview. Bare `supercheck destroy` errors without `--force`.
</Callout>

`diff` and `deploy` preserve remote resources absent from config by default. Use `diff --delete` to preview pruning, then `deploy --delete` to apply it. Pruning includes resources created outside this config. `--no-delete` remains supported. `--force` skips the confirmation prompt; keep test scripts as editable source files and review `supercheck diff` before deploying.

<Accordions>
<Accordion title="supercheck pull: files, backups and overwrites" id="supercheck-pull">

Config pulls include monitors (with tags), jobs, requirements, notification providers, variables, tags, and status pages (settings, branding, notifications and components); test pulls also write test scripts under `_supercheck_/` with `@title`, `@priority` and `@tags` annotations. Pull preserves managed test paths and existing browser and `testMatch` settings. Runner-type changes migrate files with backups; new tests must match configured custom globs or pull stops before writing.

When overwriting changed files, pull saves a mode-`0600` backup at `<path>.supercheck-backup.<uuid>`. This includes matching test scripts and config files; if a test file is renamed during pull, the old file is backed up before removal. Backups are retained and must be removed manually when no longer needed.

In JSON mode, the completed pull summary includes `files` and `backups` arrays with the paths written and preserved. `--dry-run` does not write files or create backups.

</Accordion>
<Accordion title="supercheck diff" id="supercheck-diff">

Includes requirements and status pages. Notification provider changes include nested `config` fields such as webhook `bodyTemplate`.

</Accordion>
<Accordion title="supercheck deploy: renames, --verify" id="supercheck-deploy">

Deploy pushes notification provider config and webhook body templates too. Renaming an ID-less non-test resource creates a separate resource; the old remote resource remains unless `--delete` is used. Carry its explicit ID or pull it first to update the existing resource.

`--verify` executes every browser test that this deploy created or updated once and waits for the result (up to 5 tests, `--verify-timeout <seconds>` each). Performance (k6) tests are deployed but never run implicitly, because they consume load budget; run them with `supercheck test execute` after you have approved the target, load and spend. If a verification run fails, the command exits `1` and the error message lists each failed test with its run ID (also in `--json` under `verification`) so you can inspect it instead of triggering again.

</Accordion>
<Accordion title="supercheck deploy: requirements, status pages and tags" id="supercheck-deploy-resources">

- **Requirements:** compared and pruned only when the config has a `requirements` key. Omitted `tags` or `tests` leave the remote value alone and `[]` clears it; tag names compare case-insensitively.
- **Status pages:** `subdomain` is read-only (pulled, never sent), notification flags you omit stay unchanged, and when the page declares `components`, remote-only components are removed only with `--delete` (omitting `components` leaves them all alone).
- **Tests:** `@priority` and `@tags` annotations are applied on deploy.
- **Tags:** test and monitor `tags` must already exist in the project or be declared under `tags` in the config; deploy checks this before any write, matching names case-insensitively. Requirement tags are created by the server.
- **Older servers:** before the first write, deploy checks the requirements API (when requirements are being written), the status page write API (when status pages are being written) and the monitor tag API (when an existing monitor is available to probe), and fails with an upgrade hint. A tagged monitor created in a project with no existing monitor to probe reports a missing tag API right after its create.

</Accordion>
</Accordions>

## Utilities

| Command | What it does | Key flags |
|---|---|---|
| `health` | Check API health | `--url` |
| `locations` | List available execution locations | — |
| `upgrade` | Upgrade the CLI to the latest release | `--tag <tag>`, `--package-manager <pm>`, `-y, --yes`, `--dry-run` |
| `doctor` | Check dependencies and configuration | `--strict`, `--fix` |

```bash
supercheck health
supercheck health --url https://supercheck.yourdomain.com
supercheck locations

supercheck upgrade
supercheck upgrade --tag <version>       # Install a specific version
supercheck upgrade --package-manager pnpm  # Use specific package manager (npm, pnpm, yarn, bun)
supercheck upgrade --dry-run               # Preview without installing
supercheck upgrade -y                      # Skip confirmation

supercheck doctor
supercheck doctor --strict # Exit non-zero unless deps, config and server-verified credentials are in place
supercheck doctor --fix    # Auto-install Playwright browsers; prints install hints for other deps
```

`upgrade --tag` defaults to `latest` and accepts explicit versions; `--dry-run` previews the upgrade command without executing.

<Accordions>
<Accordion title="supercheck doctor: checks, --strict and --fix" id="supercheck-doctor">

| Check | What it verifies |
|---|---|
| **Node.js** | Runtime availability |
| **@playwright/test** | npm package for browser tests |
| **Playwright browsers** | chromium binary for local test execution |
| **k6** | Binary for performance/load tests (optional) |
| **Authentication** | Whether a valid token is stored |
| **Configuration** | Whether `supercheck.config.ts` exists (it is read as text, never executed, so only literal values are understood; computed values are noted) |

If `supercheck.config.ts` names a different API than the one in use, doctor says so and does not send your token to the URL written in a repository. Set `SUPERCHECK_URL` (or run `supercheck login --url ...`) to verify against it.

Doctor verifies stored credentials against the server (`/api/context`, 5 second timeout, no retries). Offline, `authenticated` and `ready` are `false` while `cloudCredentialsPresent` stays `true`. With `--strict` the exit code is 3 for missing dependencies or config, 2 for rejected or missing credentials and 4 when the server cannot be reached.

With `--fix`, doctor installs missing Playwright browsers automatically by running `npx playwright install` in the current directory, which uses the repository's own `node_modules`: use `--fix` only in a repository you trust. For `@playwright/test` and `k6`, it prints the install command to run manually.

</Accordion>
</Accordions>
