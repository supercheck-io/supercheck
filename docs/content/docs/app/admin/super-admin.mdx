Super Admin provides platform-level management for self-hosted deployments: users, organizations, queues, locations and system health.

## Enable Super Admin

Run the bootstrap script inside the app container with the admin's email. The user must have signed up first.

```bash
docker compose exec app node scripts/bootstrap-admin.js admin@yourdomain.com
```

Without an argument the script reads `SUPER_ADMIN_EMAIL`. The app container also runs it on every start, so a `SUPER_ADMIN_EMAIL` passed into the container promotes that user at startup. Pass the variable into the container; setting it only in your host shell or `.env` does not forward it through the shipped Compose files.

```bash
docker compose exec -e SUPER_ADMIN_EMAIL=admin@yourdomain.com \
  app node scripts/bootstrap-admin.js
```

To revoke the role:

```bash
docker compose exec app node scripts/revoke-admin.js admin@yourdomain.com
```

Revoking sets the user's system role back to `project_viewer` and invalidates their sessions. Organization memberships and project assignments are managed separately.

## Deletions

The **Deletions** tab lists organizations pending deletion, then background purges in progress.

- **Purge now** skips the grace window for one organization, such as for a legal erasure request. Enter a reason of at least 10 characters and type the organization ID. The purge is audited with your reason and cannot be undone. Organization owners cannot do this.
- The purge table shows purges of organizations, projects, jobs and monitors that are queued, running or failed, with phase and last error. **Retry** gives a failed job a fresh set of attempts.

## Locations

Locations are worker execution entries for self-hosted monitoring and performance testing. Connect a worker, then enable its entry for projects.

<Steps>
<Step>
Open **Super Admin → Locations** and select **Add Location**.
</Step>
<Step>
Fill in the fields below and select **Create Location**.
</Step>
</Steps>

| Field | Required | Description |
|-------|----------|-------------|
| **Code** | Yes | Must match the worker's `WORKER_LOCATION` (such as `worker-pool`). Lowercase, 2–50 characters, letters, digits and hyphens only, no consecutive hyphens. Reserved codes (`global`, `all`, `default`, `none`, `any`, `local`, `job-scheduler`, `scheduler`) are blocked |
| **Name** | Yes | Display name, such as "Worker Pool" |
| **Region** | No | Descriptive label for administrators |
| **Flag** | No | Emoji flag for the UI |
| **Latitude**, **Longitude** | No | Coordinates for map visualization |
| **Default location** | No | Makes it the default k6 job execution location |
| **Sort Order** | No | Position in location lists |
| **Browser execution (Playwright)** | No | Allows synthetic (Playwright) monitors in this location. Off for new locations created in the dashboard |
| **Performance tests (k6)** | No | Allows k6 tests pinned to this location. Off for new locations created in the dashboard |
| **Enabled** | No | Makes the location available for new checks and runs. On by default; turn it off to stage a region before anyone can select it. A disabled location cannot be the default |

<Accordions>
<Accordion title="Workload capabilities" id="workload-capabilities">

An enabled location always runs HTTP, SSL, ping, port and MCP monitors. Browser (Playwright) and k6 workloads are opt-in per location:

- **Synthetic monitors** need **Browser execution**. In the monitor form, locations without it stay visible but disabled ("Browser checks are not available in this region."), and a monitor with such a location selected cannot be saved until you deselect it.
- **k6 tests** need **Performance tests**. `global` runs on any eligible k6 worker.
- **Playwright tests and CI jobs** have no location of their own. A project is rejected only when every location it may use is probe-only.
- Turning a capability off stops new executions shortly afterwards. Running executions finish and results are kept. Drain queued work first for a routine change: turning **Performance tests** off also stops that location's k6 workers, so k6 runs already queued there wait until it is turned back on.
- Turning a capability on takes effect without a release. For k6, the worker must already include `k6` in `WORKER_QUEUES`; otherwise add that queue role and restart the worker before enabling **Performance tests**. An eligible consumer starts after the worker refreshes its location configuration.

`WORKER_QUEUES` sets which queues a worker consumes; see [Multi-server deployment](/docs/app/deployment/multi-server#choosing-what-each-worker-runs).

</Accordion>
</Accordions>

| Status | Meaning |
|--------|---------|
| **Active** | Enabled, with workers connected (heartbeat detected) |
| **Offline** | Enabled, but no workers connected |
| **Disabled** | Unavailable for new checks and runs |

A location becomes **Active** when it is enabled and a matching worker connects. Deploy a worker with the matching `WORKER_LOCATION` to bring it online; until the location is created, the worker appears in the **Unregistered worker locations** alert, which confirms it is reaching Redis. A disabled location never shows as Active and its workers do not consume its queues. See [Self-hosted deployment](/docs/app/deployment/self-hosted) for setup.

Only one location can be the default for k6 **job** executions; choosing a new default clears the previous one. Organization admins can restrict which locations a project may use.

## User management

- **Impersonate**: log in as any user for troubleshooting.
- **Ban User** / **Unban User**: suspend an account with a reason. Banned users cannot sign in.
- **Delete User**: permanently remove an account. The dialog lists the organizations deleted with it (those where the user is the only member); type the user's email to confirm.

### Impersonate a user

<Steps>
<Step>
Open **Super Admin → Users** and the user's menu (**⋮**).
</Step>
<Step>
Select **Impersonate**. If the user belongs to several organizations, choose one.
</Step>
<Step>
Select **Impersonate User** to confirm.
</Step>
</Steps>

![Impersonate User Dialog](/screenshots/super-admin-impersonate-user.png)

A banner at the bottom shows "Impersonating" with the user's email; select **Stop** to return to your admin session. You see the platform as the user does. These are refused while impersonating: creating CLI tokens, trigger keys and recorder keys; approving a CLI device login; connecting or disconnecting MCP apps; registering or rotating Private Agents; checkout, the billing portal, billing settings and seat changes; deleting or purging organizations, cancelling an organization deletion, restoring projects and deleting users; starting another impersonation; changing the profile, credentials, sessions and linked accounts; revealing secret values or heartbeat ping URLs; and using secrets in monitors. Secret names and metadata still list; refused reveals are audited.

![Impersonation Banner](/screenshots/super-admin-impersonation-banner.png)

<Callout type="warn">
All impersonation sessions are logged for audit.
</Callout>

### Ban a user

<Steps>
<Step>
Open **Super Admin → Users** and the user's menu (**⋮**).
</Step>
<Step>
Select **Ban User**.
</Step>
<Step>
Enter a reason (minimum 20 characters), then select **Ban User** to confirm.
</Step>
</Steps>

![Ban User Dialog](/screenshots/super-admin-ban-user.png)

Banning is reversible: the user cannot sign in until unbanned, and their data is preserved. To unban, select **Unban User** from the same menu.

## Security controls

| Control | Details |
|---|---|
| **Single admin** | One super admin email per deployment |
| **Validation** | Multiple emails in `SUPER_ADMIN_EMAIL` cause a startup error |
| **Audit trail** | All super admin actions are logged with timestamps |
