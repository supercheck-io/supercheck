Project Admins and organization-level administrators configure AI SRE from **Organization Admin**. Responders start from **Alerts** or **Investigate → Incidents**. **Copilot** and **Services** are grouped under **Investigate**; the map is an optional link from an incident or service.

Select **Setup guide** beside **Add service**, **Add connector**, or **Add recipe** to review setup status.

<Callout type="info">
**Self-Hosted Requirement**: AI SRE and alert-triggered automation are enabled by default with a configured AI provider. No enable flag is required. Set `SRE_AUTOMATION_ENABLED=false` for manual-only AI work, or `SRE_ENABLED=false` to disable AI SRE. Recreate the affected app and worker containers after changing `.env`. See [Self-Hosted AI SRE Features](/docs/app/deployment/self-hosted#optional-configuration).
</Callout>

## Services

Use **Services** to define the systems responders recognize, such as `checkout-service` or `payment-gateway`.

![Services Catalog](/screenshots/sre-services-catalog.png)

Click **Add service** to register a service with its metadata, environment, and tier:

![Add Service Dialog](/screenshots/sre-add-service-dialog.png)

For each service, add its owner, environment, repository, and telemetry name. The service detail page manages:

- **Activity** opens first with recent incidents, alerts, and deployments.
- **Resources** links monitors, jobs, tests, k6 runs, and status components.
- **Dependencies** shows service relationships. Expand **Suggested dependencies** to approve or reject discoveries and review past decisions.

Service health shows its status and explanation. Nonzero incident and alert counts remain visible; expand **Service details** for tier, owner, available health score, and calculation time.

Suggested relationships do not enter the Investigation Map until an authorized user approves them.

## Integrations

Use **Organization Admin → Integrations** to add read-only evidence sources. Each connector has a service scope, validation status, execution mode, and output limits.

![Integrations & Connectors](/screenshots/sre-connectors.png)

Click **Add connector** to connect external telemetry providers like Prometheus, Grafana, Loki, or GitHub:

![Add Connector Dialog](/screenshots/sre-add-connector-dialog.png)

Use the narrowest credential and service scope that supports your investigation queries. Validate the connector after setup. See [Connectors](/docs/app/investigate/connectors) for supported providers and query examples.

Connectors are optional. Start with stored Supercheck evidence, then add external sources your team needs.

## Diagnostic Recipes

Use **Diagnostic Recipes** to save approved, repeatable investigation queries. Choose a connector, define the approved query, and set output and time limits.

Start with high-value checks such as service error rate, latency, recent error logs, or slow traces.

## Private Agents

Use a Private Agent when a supported provider is reachable only inside your network. For Supercheck Cloud, you keep using the cloud dashboard and run only the agent locally.

1. Register the agent in **Organization Admin → Private Agents**.
2. [Run it with Docker Compose](/docs/app/deployment/private-agent) inside your network and confirm it shows **connected**.
3. Add a connector in **Organization Admin → Integrations**, choose **Private Agent**, and select the registered agent.
4. Validate the connector, then enable live sources in an incident investigation when you need its evidence.

Keep provider credentials in the connector's dedicated credential fields. No inbound firewall access is required.

## Permissions

| Task | Required permission |
|---|---|
| Manage integrations, recipes, or Private Agents | Connector configure |
| Edit service metadata, dependencies, or links | Service update |
| Approve topology suggestions | Service configure |
| Create or investigate incidents | Matching incident permission |

## Optional Slack and Teams incident commands

Slack/Teams command handling is separate from normal dashboard and CLI SRE use. Skip this setup unless you want responders to acknowledge, resolve, or investigate incidents from chat.

From your deployment directory, configure only the integration you use in `.env`:

```bash
# Slack commands and replies
SLACK_SIGNING_SECRET=your-slack-signing-secret
SLACK_BOT_TOKEN=your-slack-bot-token
# Or Teams outgoing webhook commands
TEAMS_OUTGOING_WEBHOOK_SECRET=your-teams-webhook-secret
# Required for either provider: comma-separated external user IDs
SRE_COLLABORATION_ALLOWED_RESPONDER_IDS=U123,U456
```

Add the optional overlay to your usual Compose command:

```bash
curl -fsSLO https://raw.githubusercontent.com/supercheck-io/supercheck/main/deploy/docker/docker-compose-collaboration.yml
docker compose -f docker-compose.yml -f docker-compose-collaboration.yml up -d --force-recreate app
```

Use your installation's main Compose filename if it differs. Slack sends signed requests to `/api/webhooks/slack`; Teams uses `/api/webhooks/teams`. Requests require valid provider signatures and responders on the allowlist. Empty allowlists deny commands. Collaboration investigations use stored evidence; use an authenticated dashboard or CLI session with explicit live-source consent to query telemetry connectors. These commands never grant live connector access or enable provider writes.

Existing custom deployments can continue supplying the legacy `SRE_SLACK_*` or `SRE_TEAMS_*` credential aliases directly; the new optional overlay uses the provider names above. Move these credentials out of normal installation settings when upgrading.
