Incidents are the responder queue for issues that need investigation, evidence review, or recovery confirmation.

## Create an Incident

| From | How |
|---|---|
| **An alert** | Incidents open automatically when a monitor or job alert fires, with no setup beyond enabling alerts. Repeated alerts for the same target join the same incident. You can also select **Open incident** next to a failure in **Communicate → Notifications → Delivery history**. Neither path starts a full AI investigation unless the project turned on **Investigate new incidents automatically** (see [Default policy](#default-policy)) |
| **Scratch** | In **Respond → Incidents**, select **New incident** for issues that did not come from a Supercheck alert. You become the assignee |

Both paths open the incident workspace. If AI triage fails, the **Activity** feed records a *triage failed* event with the error code, so the failure is visible on the incident.

## Incident Queue

Open **Incidents** in the sidebar. **Trends** and **New incident** are in the page header. Alert notifications sent are listed under **Notifications → Delivery history** (see [Alerts](/docs/app/communicate/alerts#delivery-history)).

The queue opens on **Active** incidents. Use the quick filters **Active**, **Assigned to me**, **Unassigned**, and **All**, or narrow by severity (`SEV1` through `SEV4`), status, service, or title.

| Column | Shows |
|---|---|
| **#** | Incident number |
| **Title**, **Severity**, **Status** | What happened and how urgent it is |
| **Service** | The linked catalog service |
| **Assignee** | The person responsible, or *Unassigned* |
| **Age** | Time since detection (detection to resolution once resolved) |
| **AI** | State of the latest AI investigation |
| **Updated** | When the incident last changed. The queue sorts by it, newest first |

![Incident Queue](/screenshots/sre-incidents-queue.png)

### Statuses

The queue and incident page show six statuses. Each maps from the stored incident status.

| Status | Meaning | Stored status |
|---|---|---|
| **Triggered** | An alert opened the incident and nobody has acknowledged it | `triggered`, not acknowledged |
| **Acknowledged** | Someone is on it | `triggered`, acknowledged |
| **Investigating** | The team or the AI is looking for the cause | `investigating` |
| **Fixing** | The cause is known and a fix is being prepared or applied | `identified`, `recommendations_ready`, `user_applying_fix` |
| **Monitoring** | A fix is in place and you are watching it hold | `verifying` |
| **Resolved** | The incident is over | `resolved` |

The API, CLI, and MCP return the label as `statusLabel` next to the stored `status`. Status filters take the stored values.

### Titles

Incidents opened by an alert are titled `<target>: <alert type>`, for example *Checkout API: Monitor down* or *Nightly job: Job failed*.

## Incident Workspace

The header shows the incident number, title, status (Triggered, Acknowledged, Investigating, Fixing, Monitoring or Resolved) and severity. One primary button follows the incident: **Acknowledge**, then **Resolve incident**. The **...** menu holds **Edit incident**, **Add commander**, **Resolve incident** (before acknowledging), and **Ask Copilot**, which opens [Copilot](/docs/app/investigate/copilot) with this incident in scope.

Below the header, the page has tabs. The right-hand column stays the same on every tab: **Properties**, **Alerts**, and **Similar incidents** when there are matches.

| Tab | Contents |
|---|---|
| **Overview** | **Summary**: one paragraph from the AI, with confidence and the first next step for an investigation, **Right** / **Wrong** buttons, and **View investigation**. Before any AI analysis it shows **Run investigation**. **Activity**: a box to post updates above the event list. **Draft customer update with AI** fills the box with a customer-safe draft for you to edit. **Also post to status page** publishes the note as an update on the incident's linked status page incident and emails its subscribers (needs permission to update status pages). The feed shows old → new values for edits, severity and status changes, reassignments, the alert that was linked, and one line for each **AI triage**, **AI investigation** and **Evidence brief** |
| **Investigation** | One report: run controls, **Conclusion** with the first three next steps (**Show all** for the rest), **Hypotheses** (each with a green, amber or grey icon and badge for validated, inconclusive or ruled out), **Evidence** with an icon for each type, and a collapsed **How it was investigated** step log |
| **Post-mortem** | Shown once the incident is resolved. See [Post-mortem](#post-mortem) |

The **Properties** card shows **Time to acknowledge** and **Time to resolve** (or **Open for** while the incident is open), then the assignee (and an optional commander), service, start time, **Status page** state with **Post update**, and a **Notifications** row with a **Watch** / **Unwatch** button. The **Alerts** card lists the linked alerts. Each **Activity** row has an icon for its kind of event and shows how long ago it happened; hover the time for the exact date.

The open tab is kept in the URL: `?tab=investigation` or `?tab=postmortem` (Overview has no parameter). The older links still work: `?tab=evidence` opens the Investigation tab at the evidence list, `?tab=brief` opens it at the conclusion, and a `#sre-evidence-<id>` link scrolls to that item.

![Incident Workspace Overview](/screenshots/incident-workspace-overview.png)

If an incident cannot be opened, the page says whether it was not found, you do not have access, or loading failed. It offers **Try again** (for a failed load) and a link back to **Incidents**.

### AI summary

The summary card and the Investigation tab answer these questions in order. The card shows a short version; the tab shows the full report.

| Part | What it tells you |
|---|---|
| **Conclusion** | What changed, the blast radius, the strongest signals, and the likely cause |
| **Confidence** | **High**, **Medium**, **Low**, or **Inconclusive**. Only an investigation is rated; an evidence brief or a triage summary is labelled as such and has no rating |
| **Recommended next steps** | Safe checks to run next. The card shows the first one |
| **Hypotheses** | Ranked explanations, each marked **Validated**, **Ruled out**, or **Inconclusive**, with a short rationale and its evidence |

**Inconclusive** is a normal result, not a failure. When the evidence does not establish a cause, the agent says what is missing and lists safe next checks instead of guessing. A hypothesis is only **Validated** when it cites real evidence from this incident. Runs whose output could not be validated show a plain summary without hypotheses or a confidence rating.

On the Investigation tab, **How it was investigated** lists each check the agent ran, a short summary of its arguments (secrets are never shown) and how many results came back. It is collapsed once the run is done and updates live while a run is in progress.

### Run, re-run, and give feedback

| Control | What it does |
|---|---|
| **Run investigation** / **Run again** | Starts a bounded, read-only AI pass over stored evidence and optional live connectors. Only one run can be active per incident; starting another returns `409` until it finishes |
| **Run options** | Opens **Include live sources** (off by default; needs a linked service and connector investigation permission) and **Re-run with my note** |
| **Right** / **Wrong** | On the whole investigation or on any single hypothesis, with an optional one-line note (up to 500 characters). Needs permission to update incidents |
| **Re-run with my note** | In **Run options**. Starts a new investigation that also sees your note as guidance, plus the notes you left on earlier runs |
| **Save report snapshot** | In the Investigation tab's **More** menu once a run completes. Locks the sanitized report for audit and review |

Your notes are hints, not evidence. Recent notes on other incidents of the same service are also passed to future investigations as hints. If a run fails or times out, review the error and available evidence before retrying.

### Similar incidents

The **Similar incidents** card in the right-hand column (shown only when there are matches) lists up to five **resolved incidents from the last 180 days** (the top three first, with **Show all** for the rest) in the same project that share the primary service, the alert source, or words in the title. It shows why each one matched and how it was resolved. A past root cause is context only: the investigation does not copy it without evidence from the current incident.

### Evidence

The **Evidence** section of the Investigation tab lists observations from Supercheck checks and connected systems.

| Item | Contents |
|---|---|
| **Evidence items** | Observations such as HTTP response codes, latency spikes, test assertions, and traces |
| **Evidence brief** | A quick AI summary of the saved evidence (**Summary**, **Impact**, **Likely cause**, **Evidence gaps**, **Next checks**). It is the **Conclusion** until an investigation has run (ahead of the AI triage finding), and it can be copied or downloaded as Markdown. **Generate brief** / **Regenerate brief** are offered until an investigation completes; after that the investigation is the report, and a brief never replaces its conclusion or confidence |

![Investigation tab](/screenshots/incident-evidence-brief.png)

<Callout type="info">
Stored evidence stays available when a connector is disabled. Disabling a connector stops new live searches but does not remove evidence already collected. **Save report snapshot** and the **Evidence brief** can be downloaded to share; credentials and raw connector responses are excluded.
</Callout>


## Post-mortem

When an incident is resolved, the **Post-mortem** tab offers **Generate post-mortem draft**. The draft is built from the activity feed, the resolution summary, the hypotheses, and the evidence titles, in these sections: **Summary**, **Impact**, **Timeline**, **Root cause**, **Contributing factors**, and **Follow-ups**. It opens as a read-only document; a section with nothing in it shows **Not written yet**.

The **Timeline** lists the key moments in UTC, named as in the Activity feed: when the incident was created, alerts linked, AI triage and investigations, acknowledgement, notes, recovery and resolution. Evidence briefs, reassignments and edits are left out, and back-to-back investigations are shown once, as the latest result. The tab shows the timeline grouped by day. Each moment has its time in a bold column on the left, an icon that matches the Activity feed (or fits the sentence), and what happened, with "All times in UTC" stated once at the top. It reads lines such as `- 6 Oct 2026, 14:58 UTC: <what happened>` and ISO timestamps such as `- 2026-10-26T23:49:24Z — <what happened>`; if any line has another shape, the tab shows the text as written. When an incident has no stored evidence, the "no evidence yet" notice is not used as the root cause, the resolution or a timeline detail.

![Post-mortem tab with the timeline grouped by day](/screenshots/incident-postmortem.png)

| Behavior | Detail |
|---|---|
| **Drafting** | If AI is unavailable, your organization's usage limit is reached, or the model returns something unusable, a template filled from the incident record is used instead. Sections without recorded facts are left empty for you to fill in. Nothing is invented |
| **Editing** | **Edit** turns every section into a text field. Follow-ups are a list you can add to and remove from. **Save post-mortem** keeps your edits; **Cancel** discards them. Unsaved edits survive switching tabs |
| **Regenerate / Export** | **Regenerate draft** replaces the text after you confirm. The download button (**Export Markdown**) next to it saves a `.md` file |
| **Limits** | Five drafts per person per incident per hour. Drafting needs permission to update incidents; people with view access can read and export |

Review the draft before sharing it. The **Activity** feed and resolution summary remain the record of what happened.

<Accordion title="How Alerts Become Incidents" id="how-alerts-become-incidents">

When a monitor or job alert fires (alerts enabled, a channel attached, outside a maintenance window), Supercheck opens an incident for it. This needs only `SRE_ENABLED` (on by default), not an AI provider, and happens even if the alert delivery fails.

**Monitors need no channel for incidents.** With **Open an incident when this alerts** on, a monitor opens, updates and resolves incidents even when it has no notification channel, and a monitor with alerts turned off can still open incidents if you switch that option on (it is off by default when alerts are off). The monitor sends no alert in those cases. The incident itself can still notify people: an assignee or service owner may receive incident emails, as for any incident. Jobs still open incidents from their delivered alerts.

**Alert count.** Each incident shows how many alerts it has absorbed: 1 when it opens, plus one for every repeat alert while it stays open, with the time of the latest. It appears in the incident list (**Alerts** column), the incident sidebar, the API (`alertCount`, `lastAlertAt`) and the MCP `get_incident` tool.

| Rule | Behavior |
|---|---|
| **One incident per source** | While an incident for a monitor or job is open, further failures join it as linked alerts. If the check fails again after a *recovered* note, the **Activity** feed shows **Failure returned** and the next recovery is noted again |
| **Severity** | *Auto* derives SEV1 to SEV4 from the alert; a fixed level in the check's settings overrides it |
| **Auto-resolve** | On recovery, an unacknowledged incident resolves itself with a note, even if recovery alerts are off. An acknowledged one stays open, gets a *recovered* note, and its participants are emailed. Applies to monitor-down and job failed or timed-out alerts; SSL-expiry incidents stay open until someone resolves them |
| **Safety sweep** | Every minute the app also checks for two lost signals. An open, unacknowledged, automatically opened incident that last alerted within the past two days, and whose monitor is up again (or whose job's latest run passed) after the incident's last alert is resolved as above, if **Resolve automatically** is on and the check's recovery threshold is 1; a longer threshold is left to the recovery signal from the worker, since the streak cannot be proven from stored state. An incident whose only automatic AI triage run was lost to an app restart (marked failed as stale) is triaged once more, within two days of opening, through the same gates as the first run: automation flag, AI configuration, billing and the organization's run limit. It never retries a second time. Older stuck incidents are left for their owners, so a long outage does not send a burst of resolved notices. Triage retries respect the organization's daily AI token limit. A project that turned on automatic investigation retries under that policy even when `SRE_AUTOMATION_ENABLED` is off, because the flag gates only instance-wide triage. Incidents created by hand are never touched. Only one app replica runs each sweep |
| **Reopen** | A new failure within 30 minutes of an automatic resolution reopens the same incident. Reopening keeps the previous resolution summary. For monitor-down and job failed or timed-out alerts only, **Open incident** from delivery history follows the same rules: it joins the source's open incident or reopens a recently auto-resolved one instead of creating a duplicate. An alert older than 30 minutes only joins an open incident and never reopens one. Changing a resolved incident's status in **Edit** also reopens it and clears its acknowledgement |

Control this per check under **Alert Settings → Incidents**: **Open an incident when this alerts**, **Severity**, and **Resolve automatically on recovery if nobody acknowledged it** (both toggles on by default).

<Callout type="info">
AI triage is separate and optional. Triage that starts by itself from an alert runs only when an administrator enables it (`SRE_AUTOMATION_ENABLED`) and an AI provider is configured. That setting gates only alert-triggered triage: running triage manually from an incident needs only `SRE_ENABLED` and an AI provider.
</Callout>

</Accordion>

<Accordion title="Ownership and Acknowledgement" id="ownership">

| Action | Behavior |
|---|---|
| **Default assignee** | An incident opened from an alert is assigned to the linked service's owner, when one is set and can still act on incidents. Set it in **Services → Edit → Owner** (a project editor or admin). Without an owner, alert incidents open unassigned until someone acknowledges or assigns them |
| **Assign** | Choose any organization owner or admin, or a project admin or editor of this project. Viewers and people outside the project are rejected. |
| **Acknowledge** | Stamps who acknowledged and when. If the incident is unassigned, the acknowledger becomes the assignee. A resolved incident can't be acknowledged. |
| **Commander** | Optional single incident commander, set from the **Properties** panel or **Add commander** |

Assignments, acknowledgements, status changes, and resolution all appear in the **Activity** feed and in the audit log.

</Accordion>

<Accordion title="Incident notifications" id="notifications">

Supercheck announces an incident when it is **opened**, **assigned**, **acknowledged**, gets an **AI finding**, **reopens**, or is **resolved**.

| Where | What is sent |
|---|---|
| **The check's channels** | Assignment, acknowledgement, AI findings, and resolution or reopening by a person. Opening, recovery, automatic resolution and automatic reopening post nothing extra, because the alert and recovery already went there. If every delivery of the opening alert failed, the channels get the incident-opened message instead |
| **Participant email** | The assignee and the incident commander get a direct email for every change someone else makes: assignment, acknowledgement, resolution and reopening, plus recovery and automatic reopening. They also get note and severity emails, even if they unwatch. On a reassignment the previous assignee is told too. You are never emailed about your own change, and only people who can still act on the incident (owners, admins, and the project's admins and editors) receive mail. Requires email delivery |
| **Watchers** | Anyone who watches an incident gets an email for each new note and each severity change (never about their own), at most one per type every 5 minutes. The creator, the assignee and everyone who comments are added automatically; **Unwatch** opts a person out. Viewers can watch |
| **Incidents without a monitor or job** | Incidents created by hand or by a connector use the project's **Default policy** (below) instead of source channels. Notes and severity changes go to people by email, never to channels |
| **Nobody to tell** | If a new incident is unassigned and no channel will be notified, the project's owners and admins are emailed |

### Default policy

Each project has one **Default policy**, edited from **Organization → Projects → ... → Incident notifications**.

| Setting | Effect |
|---|---|
| **Channels** | Up to 10. Notified about incidents created by hand or by a connector, and about reminders for every incident. Monitors and jobs keep the channels chosen on them |
| **Email the service owners for SEV1 and SEV2** | Also emails the incident's service owners when a SEV1 or SEV2 opens |
| **Remind if nobody acknowledges** | First reminder after the chosen minutes (5 to 1,440) from when the incident opened, or from its latest reopening; **then every** M minutes (off reminds once); **at most** K reminders in total (1 to 10, default 3). Each goes to the policy channels and the assignee and commander. The whole schedule must finish within two days, and incidents more than two days old are not reminded. Off by default |
| **Escalate if still unacknowledged** | Once, after the chosen minutes (5 to 1,440), to one channel **or** one project member (by email). A paging service cannot be the target. If the channel or member was removed, the timeline records that nobody was escalated to |
| **Investigate new incidents automatically** | Off by default because full investigations count toward your AI SRE investigation allowance. SEV1 and SEV2 get a full investigation, SEV3 and SEV4 a quick triage, through the same plan and usage limits as starting one by hand. Only incidents opened after you turn it on are covered, and automatic runs use stored evidence, not live sources. A manual run of another type doesn't block the automatic one. A failed automatic run is tried again on a later trigger, up to three attempts. It doesn't start while three runs are already in progress in the organization |

Reminders and escalation stop when someone acknowledges or resolves the incident, or lowers its severity (raising it does not restart them). A reopen starts the schedule again. They wait while a scheduled status-page maintenance covers the incident's monitor and resume after it, and each organization gets at most 30 reminder and escalation sends per hour, so a flapping monitor cannot flood channels. Every reminder and escalation is recorded on the incident timeline with the channels it reached. The CLI reads and changes these settings with `supercheck incident policy get` and `supercheck incident policy set`; the MCP tool `get_incident_policy` reads them.

Email, Slack, Teams, Discord, Telegram and plain webhook channels are supported; paging services (webhooks with a preset or body template) are skipped for incident messages, reminders and escalation, because monitor and job alerts already page them. Each message names the incident, severity and service and links to it, without raw evidence, logs, credentials or AI conclusions. Recovery and reopen emails reach each person at most once every 10 minutes, so a flapping check does not flood inboxes.

</Accordion>

<Accordion title="Incident Lifecycle" id="lifecycle">

| Stage | Who | Action |
|---|---|---|
| **Triage** | Responder / Supercheck | An incident opens automatically from an alert (or create one manually). AI triage and correlation depend on administrator configuration |
| **Investigate** | AI SRE agent | Reads native evidence and authorized connectors, then generates cited hypotheses |
| **Decide and fix** | Responder | Evaluates findings and applies remediation in external systems |
| **Confirm recovery** | Responder | Re-runs synthetic tests, checks monitors, or observes metrics |
| **Acknowledge** | Responder | Select **Acknowledge** to take ownership; the incident is assigned to you if nobody else holds it |
| **Resolve** | Responder | Select **Resolve incident**. A resolution summary is required (up to 2,000 characters) and is pre-filled from the recovery (when the checks that raised the incident are passing again) and the AI root cause. Edit it to state the fix and the checks that confirmed recovery |

Resolving records your decision and the summary on the incident and its **Activity** feed. It does not run checks or apply remediation. Closing an incident through the edit dialog is not available; use **Resolve incident**.

</Accordion>

<Accordion title="Rate limits and trial allowance" id="trial-allowance">

Limits apply per person and incident, and exceeding one returns `429` with a retry delay.

| Action | Limit |
|---|---|
| **Triage** | 10 starts per 5 minutes |
| **Investigation** | 3 starts per 5 minutes |
| **Evidence brief** | 3 per minute |
| **Copilot chat** | 30 messages per minute per person |

Only one investigation or triage run can be active per incident (`409` otherwise).

On the free trial, AI triage is limited to 20 runs and investigations to the trial's included number. A run that fails does not count against either. Copilot chat and evidence briefs need a paid plan.

</Accordion>

<Accordion title="Permissions" id="permissions">

| Role | View | Investigate stored evidence | Live sources | Assign, acknowledge, resolve, post updates |
|---|:---:|:---:|:---:|:---:|
| Org Owner, Org Admin, Project Admin | ✓ | ✓ | ✓ | ✓ |
| Project Editor | ✓ | ✓ | — | ✓ |
| Project Viewer | ✓ | — | — | — |

The same `sre_incident:update` permission covers assign, acknowledge, resolve, and updates over the API (`POST /api/sre/incidents/{id}/assign`, `/acknowledge`, `/resolve`).

If investigations are disabled, existing evidence and results stay readable, but run and live-source controls are unavailable.
