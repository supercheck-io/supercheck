Incidents are the responder queue for issues that need investigation, evidence review, or recovery confirmation.

## Create an Incident

| From | How |
|---|---|
| **An alert** | In **Communicate → Alerts → Signals**, select **Investigate** next to a failure. Repeated deliveries are grouped, and the latest alert opens a new or existing incident without starting a full investigation |
| **Scratch** | In **Investigate → Incidents**, select **New incident** for issues that did not come from a Supercheck alert |

Both paths open the incident workspace.

![Create Incident Dialog](/screenshots/create-incident-dialog.png)

## Incident Queue

The queue opens on **Active** incidents. Use the quick filters **Active**, **Assigned to me**, **Unassigned**, and **All**, or narrow by severity (`SEV1` through `SEV4`), status, service, or title.

| Column | Shows |
|---|---|
| **#** | Incident number |
| **Title**, **Severity**, **Status** | What happened and how urgent it is |
| **Service** | The linked catalog service |
| **Assignee** | The person responsible, or *Unassigned* |
| **Age** | Time since detection (detection to resolution once resolved) |
| **AI** | State of the latest AI investigation |

Quick actions open **Review alerts** and **Trends**. A project with no incidents yet shows a short checklist: connect a source, enable alerts, run a sample investigation.

![Incident Queue](/screenshots/sre-incidents-queue.png)

## Incident Workspace

The header shows the title, severity, status, and **assignee**, with the primary actions **Acknowledge**, **Assign**, **Investigate**, and **Resolve incident**. The main column leads with the **AI summary** (conclusion and confidence, or *Inconclusive* when the evidence does not support a cause), followed by the **timeline** with a box to post updates. The right sidebar shows the optional **commander**, service, linked alerts, the status-page link with **Publish update**, and timestamps with MTTA and MTTR.

Below the timeline, the workspace has two tabs.

## Investigation Report

Reports label statements as **Fact**, **Inference**, or **Hypothesis**.

| Section | Contents |
|---|---|
| **What changed** | Recent commits, deployments, or configuration updates |
| **Blast radius** | Affected endpoints, services, and downstream dependencies |
| **Strongest signals** | High-confidence failure patterns and error messages |
| **Likely cause & confidence** | Root cause hypothesis with rationale |
| **Evidence gaps** | Missing data or unchecked systems |
| **Next safe checks** | Recommended read-only checks to verify state |

If the evidence cannot determine a root cause, the report states the gap instead of guessing.

Use **Save report** to keep the findings of a completed investigation. Generate an **Evidence brief** separately for a shorter summary. Download either to share with your team. Review evidence gaps and incomplete results first. Credentials and raw connector responses are excluded.

## Ownership and Acknowledgement

| Action | Behavior |
|---|---|
| **Default assignee** | Incidents opened from alerts are assigned to the primary owner of the linked service when that person is still a member who can act on incidents. Otherwise they stay unassigned |
| **Assign** | Choose any organization owner or admin, or a project admin or editor of this project. Viewers and people outside the project are rejected. Assigning again to the same person changes nothing |
| **Acknowledge** | Stamps who acknowledged and when. If the incident is unassigned, the acknowledger becomes the assignee. Acknowledging twice is harmless |
| **Commander** | Optional single incident commander, set from the sidebar |

Assignments, acknowledgements, status changes, and resolution all appear on the timeline and in the audit log.

## Notifications

Supercheck announces an incident when it is **opened**, **assigned**, **acknowledged**, receives an **AI finding**, and when it is **resolved**.

- The new assignee also gets a direct email (not for their own actions), when email delivery is configured.
- Messages go through the notification channels already attached to the monitor or job that raised the alert. Incidents created by hand have no source alert, so only the assignee is emailed when you assign them.
- Email, Slack, Teams, Discord, Telegram and webhook channels are supported. A webhook that uses a preset or a custom body template is skipped for incident messages, because they use a fixed JSON body; attach a plain webhook channel to receive them.
- Each message names the incident, severity, and service, and links back to the incident page. It never contains raw evidence, logs, credentials, or AI-generated text; open the incident to read the AI finding.
- The same event for the same incident is announced once within a short window, so retries and repeated AI runs do not flood a channel.

## Incident Lifecycle

| Stage | Who | Action |
|---|---|---|
| **Triage** | Responder / Supercheck | Select **Investigate** on an alert signal or create an incident manually. Automatic correlation depends on administrator configuration |
| **Investigate** | AI SRE agent | Reads native evidence and authorized connectors, then generates cited hypotheses |
| **Decide and fix** | Responder | Evaluates findings and applies remediation in external systems |
| **Confirm recovery** | Responder | Re-runs synthetic tests, checks monitors, or observes metrics |
| **Acknowledge** | Responder | Select **Acknowledge** to take ownership; the incident is assigned to you if nobody else holds it |
| **Resolve** | Responder | Select **Resolve incident**. A resolution summary is required (up to 2,000 characters) and is pre-filled from the AI root cause when one exists. Edit it to state the fix and the checks that confirmed recovery |

Resolving records your decision and the summary on the incident and its timeline. It does not run checks or apply remediation. Closing an incident through the edit dialog is not available; use **Resolve incident**.

<Callout type="info">
A post-mortem draft generated from the timeline is planned. Today the resolution summary and timeline are the written record.
</Callout>

## Incident Trends

Select **Trends** in the queue to see metrics for the last 30 days.

| Metric | Shows |
|---|---|
| **Volume** | Incidents created vs. resolved |
| **Resolution rate and average resolution time** | Percentage resolved and mean time to resolution |
| **Severity mix** | Breakdown across SEV1 to SEV4 |
| **Most affected services** | Hotspots that need deeper fixes |

Open **Investigate → Copilot**, or select **Open Copilot** on an incident. See [Copilot Chat](/docs/app/investigate/copilot) for modes, live sources, and limits.

## Alerts vs. Incidents

| Open | To |
|---|---|
| **Alerts** | Review failure signals, delivery history, and notification channels |
| **Incidents** | Investigate evidence, save findings, and record recovery |

## Permissions

| Role | View | Investigate stored evidence | Live sources | Assign, acknowledge, resolve, post updates |
|---|:---:|:---:|:---:|:---:|
| Org Owner, Org Admin, Project Admin | ✓ | ✓ | ✓ | ✓ |
| Project Editor | ✓ | ✓ | — | ✓ |
| Project Viewer | ✓ | — | — | — |

The same `sre_incident:update` permission covers assign, acknowledge, resolve, and updates over the API (`POST /api/sre/incidents/{id}/assign`, `/acknowledge`, `/resolve`).

If investigations are disabled, existing evidence and results stay readable, but run and live-source controls are unavailable.
