Incidents are the responder queue for issues that need investigation, evidence review or recovery confirmation.

## Create an incident

| From | How |
|---|---|
| **An alert** | Opens automatically when a monitor or job alert fires. Repeated alerts for the same target join the same incident. You can also select **Open incident** next to a failure in **Communicate → Notifications → Delivery history**. Neither path starts a full AI investigation unless the project turned on **Investigate new incidents automatically** (see [Default policy](#default-policy)) |
| **By hand** | For a problem no alert caught, such as a customer report: **New incident** on **Respond → Incidents**, **Declare incident** in Quick Create or the command menu (Cmd+K), or **Declare incident** on a service or monitor page (prefilled). Also `supercheck incident create`, `POST /api/sre/incidents` and the MCP tool `create_incident` |

Both paths open the incident workspace. If AI triage fails, the **Activity** feed records a *triage failed* event with the error code.

![Create Incident Dialog](/screenshots/create-incident-dialog.png)

### Declare an incident

Only the title and severity are required; the rest can change later.

| Field | Effect |
|---|---|
| **Service** | Sets the service. Its owner becomes the assignee, as for alert-opened incidents; without a service, you are the assignee |
| **Affected monitors** | The next alert from a listed monitor, or from a monitor mapped to a listed service, joins this incident instead of opening a new one, even if the monitor has **Open incidents** turned off. It joins as a related alert, so the monitor recovering does not resolve the incident: a person declared it, so a person resolves it. Listed under **Affected** in the sidebar; editable until the incident is resolved |
| **Commander** | A project editor or admin; gets the incident emails |
| **Post to a status page** | Also posts a public incident on the chosen components with an impact and a first message (needs status page permission). Subscribers are emailed only if **Notify subscribers** is on. If the public post fails, the incident is still created, the Activity feed records it, and you can post again from the status page's **Status updates** tab |

A declared incident gets the same numbering, Activity entries, Default policy notifications, reminders and automatic investigation as an alert-opened one. Declaring is limited to 10 per minute per person and 60 per hour per organization. On Supercheck Cloud, an organization with no paid plan and no active trial cannot declare incidents (`402`, `subscription_required`), and an incident it opens does not start an automatic investigation.

## Incident queue

Open **Incidents** in the sidebar. **Trends** and **New incident** are in the page header. The queue opens on **Active**; use the quick filters **Active**, **Assigned to me**, **Unassigned** and **All**, or narrow by severity (`SEV1` to `SEV4`), status, service or title.

| Column | Shows |
|---|---|
| **#** | Incident number |
| **Title**, **Severity**, **Status** | What happened and how urgent it is |
| **Service** | The linked catalog service |
| **Assignee** | The person responsible, or *Unassigned* |
| **Age** | Time since detection (detection to resolution once resolved) |
| **AI** | State of the latest AI investigation |
| **Updated** | Last change. The queue sorts by it, newest first |

![Incident Queue](/screenshots/sre-incidents-queue.png)

### Statuses

Six statuses map from the stored status. The API, CLI and MCP return the label as `statusLabel` next to the stored `status`; status filters take the stored values.

| Status | Meaning | Stored status |
|---|---|---|
| **Triggered** | An alert opened it and nobody has acknowledged it | `triggered`, not acknowledged |
| **Acknowledged** | Someone is on it | `triggered`, acknowledged |
| **Investigating** | The team or the AI is looking for the cause | `investigating` |
| **Fixing** | The cause is known; a fix is being prepared or applied | `identified`, `recommendations_ready`, `user_applying_fix` |
| **Monitoring** | A fix is in place and you are watching it hold | `verifying` |
| **Resolved** | The incident is over | `resolved` |

Alert-opened incidents are titled `<target>: <alert type>`, for example *Checkout API: Monitor down*.

## Incident workspace

The header shows the number, title, status and severity. One primary button follows the incident: **Acknowledge**, then **Resolve incident**. The **...** menu holds **Edit incident**, **Add commander**, **Resolve incident** (before acknowledging) and **Ask Copilot**, which opens [Copilot](/docs/app/investigate/copilot) with this incident in scope.

![Incident Workspace Overview](/screenshots/incident-workspace-overview.png)

| Tab | Contents |
|---|---|
| **Overview** | **Summary**: one AI paragraph with confidence and the first next step, **Right** / **Wrong** buttons and **View investigation**; before any analysis, **Run investigation**. **Activity**: a box to post updates above the event list. **Draft customer update with AI** fills the box with a customer-safe draft to edit. **Also post to status page** publishes the note on the linked status page incident and emails its subscribers (needs permission to update status pages). The feed shows old → new values for edits, severity and status changes, reassignments, linked alerts, and one line each for **AI triage**, **AI investigation** and **Evidence brief** |
| **Investigation** | **Conclusion** with the first three next steps (**Show all** for the rest), **Hypotheses** (green, amber or grey for validated, inconclusive or ruled out), **Evidence** with an icon per type, run controls, and a collapsed **How it was investigated** step log |
| **Post-mortem** | Shown once the incident is resolved. See [Post-mortem](#post-mortem) |

The right-hand column is the same on every tab: **Properties**, **Alerts** (linked alerts) and **Similar incidents** when there are matches. **Properties** shows **Time to acknowledge** and **Time to resolve** (or **Open for**), the assignee, optional commander, service, start time, **Status page** state with **Post update**, and a **Notifications** row with **Watch** / **Unwatch**. Hover an Activity time for the exact date.

The open tab is kept in the URL: `?tab=investigation` or `?tab=postmortem` (Overview has no parameter). Older links still work: `?tab=evidence` opens the evidence list, `?tab=brief` opens the conclusion, and `#sre-evidence-<id>` scrolls to that item.

If an incident cannot be opened, the page says whether it was not found, you lack access, or loading failed, with **Try again** (failed load) and a link back to **Incidents**.

### AI summary

The summary card shows a short version; the Investigation tab shows the full report.

| Part | What it tells you |
|---|---|
| **Conclusion** | What changed, the blast radius, the strongest signals and the likely cause |
| **Confidence** | **High**, **Medium**, **Low** or **Inconclusive**. Only an investigation is rated; an evidence brief or triage summary is labelled as such |
| **Recommended next steps** | Safe checks to run next. The card shows the first |
| **Hypotheses** | Ranked explanations, each **Validated**, **Ruled out** or **Inconclusive**, with a rationale and evidence |

**Inconclusive** is a normal result. When the evidence does not establish a cause, the agent says what is missing and lists safe next checks. A hypothesis is **Validated** only when it cites real evidence from this incident. Runs whose output could not be validated show a plain summary without hypotheses or confidence.

**How it was investigated** lists each check the agent ran, a short summary of its arguments (secrets are never shown) and how many results came back. A failed step shows a short, redacted reason. It updates live during a run and collapses when done.

### Run, re-run and give feedback

| Control | What it does |
|---|---|
| **Run investigation** / **Run again** | Starts a bounded, read-only AI pass over stored evidence and optional live connectors. One run per incident at a time; another start returns `409` until it finishes |
| **Run options** | **Include live sources** (on by default when the project has a valid connector; needs a linked service and connector investigation permission; the run is told each connector's id, type and query language, and the service's OTel name) and **Re-run with my note** |
| **Right** / **Wrong** | On the whole investigation or one hypothesis, with an optional note up to 500 characters. Needs permission to update incidents |
| **Re-run with my note** | Starts a new investigation that also sees your note, plus notes from earlier runs |
| **Save report snapshot** | In the Investigation tab's **More** menu after a run completes. Locks the sanitized report for audit |

Notes are hints, not evidence. Recent notes on other incidents of the same service are also passed to future investigations as hints. If a run fails or times out, review the error and evidence before retrying.

### Similar incidents

Lists up to five **resolved incidents from the last 180 days** in the same project that share the primary service, alert source or title words (top three first, **Show all** for the rest), with why each matched and how it was resolved. A past root cause is context only; the investigation does not copy it without current evidence.

### Evidence

| Item | Contents |
|---|---|
| **Evidence items** | Observations such as HTTP response codes, latency spikes, test assertions and traces |
| **Evidence brief** | A quick AI summary of saved evidence (**Summary**, **Impact**, **Likely cause**, **Evidence gaps**, **Next checks**). It is the **Conclusion** until an investigation has run, and can be copied or downloaded as Markdown. **Generate brief** / **Regenerate brief** are offered until an investigation completes; a brief never replaces an investigation's conclusion or confidence |

![Investigation tab](/screenshots/incident-evidence-brief.png)

<Callout type="info">
Disabling a connector stops new live searches but keeps evidence already collected. **Save report snapshot** and the **Evidence brief** can be downloaded to share; credentials and raw connector responses are excluded.
</Callout>

## Post-mortem

On a resolved incident, **Generate post-mortem draft** builds a read-only document from the activity feed, resolution summary, hypotheses and evidence titles: **Summary**, **Impact**, **Timeline**, **Root cause**, **Contributing factors** and **Follow-ups**. An empty section shows **Not written yet**.

The **Timeline** lists key moments in UTC, named as in the Activity feed: creation, linked alerts, AI triage and investigations, acknowledgement, notes, recovery and resolution. Evidence briefs, reassignments and edits are left out, and back-to-back investigations appear once, as the latest result. The tab groups moments by day, with the time in a bold column, an icon matching the Activity feed, and "All times in UTC" stated once. It reads lines such as `- 6 Oct 2026, 14:58 UTC: <what happened>` and `- 2026-10-26T23:49:24Z — <what happened>`; other shapes show as written. With no stored evidence, the "no evidence yet" notice is not used as the root cause, resolution or a timeline detail.

![Post-mortem tab with the timeline grouped by day](/screenshots/incident-postmortem.png)

| Behavior | Detail |
|---|---|
| **Drafting** | If AI is unavailable, your organization's usage limit is reached, or the model returns something unusable, a template filled from the incident record is used. Sections without recorded facts stay empty. Nothing is invented |
| **Editing** | **Edit** turns every section into a text field; follow-ups are a list. **Save post-mortem** keeps edits, **Cancel** discards them. Unsaved edits survive switching tabs |
| **Regenerate / Export** | **Regenerate draft** replaces the text after you confirm. **Export Markdown** saves a `.md` file |
| **Limits** | Five drafts per person per incident per hour. Drafting needs permission to update incidents; view access can read and export |

Read it outside the app with `supercheck incident postmortem <id>` or `GET /api/sre/incidents/{id}/postmortem`. Review the draft before sharing; the **Activity** feed and resolution summary remain the record.

<Accordion title="How alerts become incidents" id="how-alerts-become-incidents">

When a monitor or job alert fires (alerts enabled, a channel attached, outside a maintenance window), Supercheck opens an incident. This needs no AI provider and happens even if alert delivery fails.

**Monitors need no channel for incidents.** With **Open an incident when this alerts** on, a monitor opens, updates and resolves incidents without a notification channel. A monitor with alerts off can still open incidents if you switch that option on (off by default when alerts are off). No alert is sent in those cases, but the assignee or service owner may receive incident emails. Jobs open incidents from their delivered alerts.

**Alert count.** Each incident counts the alerts it absorbed: 1 when it opens, plus one per repeat alert while open, with the time of the latest. It appears in the **Alerts** column, the sidebar, the API (`alertCount`, `lastAlertAt`) and the MCP `get_incident` tool.

| Rule | Behavior |
|---|---|
| **One incident per source** | While an incident for a monitor or job is open, further failures join it as linked alerts. If the check fails again after a *recovered* note, the **Activity** feed shows **Failure returned** and the next recovery is noted again |
| **Severity** | *Auto* derives SEV1 to SEV4 from the alert; a fixed level in the check's settings overrides it |
| **Auto-resolve** | On recovery, an unacknowledged incident resolves itself with a note, even if recovery alerts are off. An acknowledged one stays open, gets a *recovered* note, and its participants are emailed. Applies to monitor-down and job failed or timed-out alerts; SSL-expiry incidents stay open until someone resolves them |
| **Safety sweep** | Every minute, Supercheck resolves or re-triages incidents that missed a recovery or triage signal, so a restart does not leave one stuck. Hand-made incidents are never touched |
| **Reopen** | A new failure within 30 minutes of an automatic resolution reopens the same incident and keeps the previous resolution summary. For monitor-down and job failed or timed-out alerts, **Open incident** from delivery history follows the same rules: it joins the open incident or reopens a recently auto-resolved one instead of creating a duplicate. An alert older than 30 minutes only joins an open incident. Changing a resolved incident's status in **Edit** also reopens it and clears its acknowledgement |

Control this per check under **Alert Settings → Incidents**: **Open an incident when this alerts**, **Severity**, and **Resolve automatically on recovery if nobody acknowledged it** (both toggles on by default).

<Callout type="info">
AI triage is separate and optional. Triage that starts by itself from an alert runs only when an administrator enables it and an AI provider is configured. Running triage manually needs only an AI provider.
</Callout>

</Accordion>

<Accordion title="Ownership and acknowledgement" id="ownership">

| Action | Behavior |
|---|---|
| **Default assignee** | An alert incident is assigned to the linked service's owner, when set and still able to act on incidents. Set it in **Services → Edit → Owner** (project editor or admin). Without an owner, it opens unassigned |
| **Assign** | Any organization owner or admin, or a project admin or editor of this project. Viewers and people outside the project are rejected |
| **Acknowledge** | Stamps who and when. An unassigned incident is assigned to the acknowledger. A resolved incident cannot be acknowledged |
| **Commander** | Optional single commander, set from **Properties** or **Add commander** |

Assignments, acknowledgements, status changes and resolution appear in the **Activity** feed and the audit log. Starting an AI triage or investigation, and generating or saving a post-mortem, are audit-logged too.

</Accordion>

<Accordion title="Incident notifications" id="notifications">

Supercheck announces an incident when it is **opened**, **assigned**, **acknowledged**, gets an **AI finding**, **reopens** or is **resolved**.

| Where | What is sent |
|---|---|
| **The check's channels** | Assignment, acknowledgement, AI findings, and resolution or reopening by a person. Opening, recovery, automatic resolution and automatic reopening post nothing extra, because the alert and recovery already went there. If every delivery of the opening alert failed, the channels get the incident-opened message instead |
| **Participant email** | The assignee and commander get an email for every change someone else makes: assignment, acknowledgement, resolution, reopening, recovery and automatic reopening. They also get note and severity emails, even if they unwatch. A reassignment also tells the previous assignee. You are never emailed about your own change, and only people who can still act on the incident receive mail. Requires email delivery |
| **Watchers** | Anyone watching gets an email per new note and severity change (never their own), at most one per type every 5 minutes. The creator, assignee and commenters are added automatically; **Unwatch** opts out. Viewers can watch |
| **Incidents without a monitor or job** | Hand-made and connector incidents use the project's **Default policy** instead of source channels. Notes and severity changes go by email, never to channels |
| **Nobody to tell** | If a new incident is unassigned and no channel will be notified, the project's owners and admins are emailed |

### Default policy

Each project has one **Default policy**, edited from **Organization → Projects → ... → Incident notifications**.

| Setting | Effect |
|---|---|
| **Channels** | Up to 10. Notified about hand-made and connector incidents, and about reminders for every incident. Monitors and jobs keep the channels chosen on them |
| **Email the service owners for SEV1 and SEV2** | Also emails the service owners when a SEV1 or SEV2 opens |
| **Remind if nobody acknowledges** | First reminder after 5 to 1,440 minutes from opening or the latest reopening; **then every** M minutes (off reminds once); **at most** K reminders (2 to 10 when repeating, default 3). Each goes to the policy channels, assignee and commander. The schedule must finish within two days, and incidents over two days old are not reminded. Off by default |
| **Escalate if still unacknowledged** | Once, after 5 to 1,440 minutes, to one channel **or** one project member (by email). A paging service cannot be the target. If the target was removed or lost access, the timeline records that nobody was escalated to and the settings dialog says so; other settings can still be saved |
| **Investigate new incidents automatically** | Off by default because full investigations count toward your AI SRE investigation allowance. SEV1 and SEV2 get a full investigation, SEV3 and SEV4 a quick triage, under the same plan and usage limits as a manual start. Only incidents opened after you turn it on are covered, and automatic runs use stored evidence, not live sources. A manual run of another type does not block the automatic one. A failed automatic run is retried on a later trigger, up to three attempts. It does not start while three runs are already in progress in the organization |

Reminders and escalation stop when someone acknowledges or resolves the incident, or lowers its severity (raising it does not restart them). A reopen restarts the schedule. They wait during [maintenance windows](/docs/app/monitor#maintenance-windows). Every reminder and escalation, and any send that fails everywhere, is recorded on the timeline. The CLI reads and changes these settings with `supercheck incident policy get` and `supercheck incident policy set`; the MCP tool `get_incident_policy` reads them.

Email, Slack, Teams, Discord, Telegram and plain webhook channels are supported. Paging services (webhooks with a preset or body template) are skipped for incident messages, reminders and escalation, because monitor and job alerts already page them. Each message names the incident, severity and service and links to it, without raw evidence, logs, credentials or AI conclusions. Recovery and reopen emails reach each person at most once every 10 minutes.

</Accordion>

<Accordion title="Incident lifecycle" id="lifecycle">

| Stage | Who | Action |
|---|---|---|
| **Triage** | Responder / Supercheck | An incident opens from an alert or by hand. AI triage and correlation depend on administrator configuration |
| **Investigate** | AI SRE agent | Reads native evidence and authorized connectors, then generates cited hypotheses |
| **Decide and fix** | Responder | Evaluates findings and applies remediation in external systems |
| **Confirm recovery** | Responder | Re-runs synthetic tests, checks monitors or metrics |
| **Acknowledge** | Responder | **Acknowledge** takes ownership; the incident is assigned to you if nobody holds it |
| **Resolve** | Responder | **Resolve incident**. A resolution summary is required (up to 2,000 characters), pre-filled from recovery (when the checks that raised the incident pass again) and the AI root cause. State the fix and the checks that confirmed recovery |

Resolving records your decision and summary on the incident and its **Activity** feed. It does not run checks or apply remediation. Closing an incident through the edit dialog is not available.

</Accordion>

<Accordion title="Rate limits" id="trial-allowance">

Limits apply per person and incident; exceeding one returns `429` with a retry delay. Only one investigation or triage run can be active per incident (`409` otherwise).

| Action | Limit |
|---|---|
| **Triage** | 10 starts per 5 minutes |
| **Investigation** | 3 starts per 5 minutes |
| **Evidence brief** | 3 per minute |
| **Copilot chat** | 30 messages per minute per person |

</Accordion>

<Accordion title="Permissions" id="permissions">

| Role | View | Investigate stored evidence | Live sources | Assign, acknowledge, resolve, post updates |
|---|:---:|:---:|:---:|:---:|
| Org Owner, Org Admin, Project Admin | ✓ | ✓ | ✓ | ✓ |
| Project Editor | ✓ | ✓ | — | ✓ |
| Project Viewer | ✓ | — | — | — |

The `sre_incident:update` permission covers assign, acknowledge, resolve and updates over the API (`POST /api/sre/incidents/{id}/assign`, `/acknowledge`, `/resolve`). If investigations are disabled, existing evidence and results stay readable, but run and live-source controls are unavailable.

</Accordion>
