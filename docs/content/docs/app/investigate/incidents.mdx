Incidents are the responder queue for issues that need investigation, evidence review, or recovery confirmation.

## Create an Incident

| From | How |
|---|---|
| **An alert** | Incidents open automatically when a monitor or job alert fires, with no setup beyond enabling alerts. Repeated alerts for the same target join the same incident. You can also select **Open incident** next to a failure in **Communicate → Notifications → Delivery history**. Neither path starts a full AI investigation |
| **Scratch** | In **Respond → Incidents**, select **New incident** for issues that did not come from a Supercheck alert |

Both paths open the incident workspace.

![Create Incident Dialog](/screenshots/create-incident-dialog.png)

## Incident Queue

Open **Incidents** in the sidebar. **Trends** and **New incident** are in the page header. Alert notifications sent are listed under **Notifications → Delivery history** (see [Alerts](/docs/app/communicate/alerts#delivery-history)).

The queue opens on **Active** incidents. Use the quick filters **Active**, **Assigned to me**, **Unassigned**, and **All**, or narrow by severity (`SEV1` through `SEV4`), status, service, or title.

| Column | Shows |
|---|---|
| **#** | Incident number |
| **Title**, **Severity**, **Status** | What happened and how urgent it is |
| **Service** | The linked catalog service |
| **Assignee** | The person responsible, or *Unassigned* |
| **Age** | Time since detection (detection to resolution once resolved) |
| **AI** | State of the latest AI investigation |

![Incident Queue](/screenshots/sre-incidents-queue.png)

### Statuses

The queue and incident page show six statuses. Each maps from the stored incident status.

| Status | Meaning | Stored status |
|---|---|---|
| **Triggered** | An alert opened the incident and nobody has acknowledged it | `triggered`, not acknowledged |
| **Acknowledged** | Someone is on it | `triggered`, acknowledged |
| **Investigating** | The team or the AI is looking for the cause | `investigating` |
| **Fixing** | The cause is known and a fix is being prepared or applied | `identified`, `recommendations_ready`, `user_applying_fix` |
| **Monitoring** | A fix is in place and you are watching it hold | `verifying` |
| **Resolved** | The incident is over | `resolved` |

The API, CLI, and MCP return the label as `statusLabel` next to the stored `status`. Status filters take the stored values.

### Titles

Incidents opened by an alert are titled `<target>: <alert type>`, for example *Checkout API: Monitor down* or *Nightly job: Job failed*.

## Incident Workspace

The header shows the incident number, title, severity, status, service, and when it opened. One primary button follows the incident: **Acknowledge**, then **Resolve incident**, then **Post-mortem** once resolved. The **...** menu holds **Edit incident**, **Add commander**, **Run investigation** (**Re-run investigation** after a run), and **Ask Copilot**. Hover the info icons for a one-sentence explanation of each term.

A progress line shows the six statuses: Triggered, Acknowledged, Investigating, Fixing, Monitoring, Resolved.

| Area | Contents |
|---|---|
| **AI summary** | The conclusion (select **Show more** to expand), confidence, the top evidence, the next step, and **Right** / **Wrong** buttons. **Investigate** or **Investigation details** opens the side panel |
| **Timeline** | A box to post updates above the event list |
| **Investigation details** panel | Tabs: **Analysis** (run controls, hypotheses, step log, report snapshot), **Evidence**, **Brief**, **Similar**, and **Post-mortem** once resolved |

The **Details** sidebar shows the assignee (and an optional commander), service, **Status page** state with **Post update**, start and acknowledgement times, **Time to acknowledge** and **Time to resolve**, linked **Alerts**, and **Similar past incidents** (only when there are matches). Open the panel directly with `?tab=investigation`, `?tab=evidence`, or `?tab=brief`.

![Incident Workspace Overview](/screenshots/incident-workspace-overview.png)

### AI summary

The summary card answers four questions in order.

| Part | What it tells you |
|---|---|
| **Conclusion** | One paragraph: what changed, the blast radius, the strongest signals, and the likely cause |
| **Confidence** | **High**, **Medium**, **Low**, or **Inconclusive** |
| **Cited evidence** | Up to three evidence items the conclusion rests on. Select one to read it |
| **Hypotheses** | Ranked explanations, each marked **Validated**, **Ruled out**, or **Inconclusive**, with a short rationale and its evidence |

**Inconclusive** is a normal result, not a failure. When the evidence does not establish a cause, the agent says what is missing and lists safe next checks instead of guessing. A hypothesis is only **Validated** when it cites real evidence from this incident. Runs from before structured results, or runs whose output could not be validated, show a plain summary without hypotheses or a confidence rating.

In the **Investigation details** panel, **How I investigated** lists each check the agent ran: the tool, a short summary of its arguments (secrets are never shown), how many results came back, and how long it took. It updates live while a run is in progress.

### Run, re-run, and give feedback

| Control | What it does |
|---|---|
| **Run investigation** / **Run again** | Starts a bounded, read-only AI pass over stored evidence and optional live connectors |
| **Include live sources** | Off by default. Needs a linked service and connector investigation permission |
| **Right** / **Wrong** | On the whole investigation or on any single hypothesis, with an optional one-line note (up to 500 characters). Needs permission to update incidents |
| **Re-run with my note** | Starts a new investigation that also sees your note as guidance, plus the notes you left on earlier runs |
| **Save report snapshot** | Locks the sanitized report for audit and review (**Analysis** tab) |

Your notes are hints, not evidence. The agent is told to weigh them against the stored evidence and to ignore any instructions inside them. Recent notes on other incidents of the same service are also passed to future investigations as hints. If a run fails or times out, review the error and available evidence before retrying.

### Similar incidents

The **Similar** tab (opened from **Similar past incidents** in the sidebar) lists up to five **resolved incidents from the last 180 days** (the top three first, with **Show more** for the rest) in the same project that share the primary service, the alert source, or words in the title. It shows why each one matched and how it was resolved. The same list, shortened, is given to the investigation as *past incidents (may be unrelated)*. A past root cause is context only: the investigation does not copy it without evidence from the current incident.

### Evidence

The **Evidence** section of the panel organizes observations from Supercheck checks and connected systems.

| Item | Contents |
|---|---|
| **Evidence items** | Observations such as HTTP response codes, latency spikes, test assertions, and traces |
| **Evidence brief** | A shareable AI summary of findings, hypotheses, and gaps. Regenerate it or download it as Markdown |

![Investigation details](/screenshots/incident-evidence-brief.png)

<Callout type="info">
Stored evidence stays available when a connector is disabled. Disabling a connector stops new live searches but does not remove evidence already collected.
</Callout>


## Saving and Sharing

Use **Save report snapshot** to keep the findings of a completed investigation, and the **Evidence brief** for a shorter summary. Download either to share. Credentials and raw connector responses are excluded.

## Post-mortem

When an incident is resolved, the **Post-mortem** card offers **Generate post-mortem draft**. The draft is built from the timeline, the resolution summary, the hypotheses, and the evidence titles, in these sections: **Summary**, **Impact**, **Timeline**, **Root cause**, **Contributing factors**, and **Follow-ups**.

- One bounded AI call writes the draft. If AI is unavailable, your organization's usage limit is reached, or the model returns something unusable, you get a template filled from the incident record instead, with placeholders where facts are missing. Nothing is invented.
- Every section is editable. Follow-ups are a simple list you can add to and remove from. Select **Save post-mortem** to keep your edits.
- **Regenerate draft** replaces the current text after you confirm. **Export Markdown** downloads the post-mortem as a `.md` file.
- Drafting is limited to five drafts per person per incident per hour. It needs permission to update incidents; people with view access can read and export it.

Review the draft before sharing it. The incident timeline and resolution summary remain the record of what happened.

<Accordion title="How Alerts Become Incidents" id="how-alerts-become-incidents">

When a monitor or job alert fires (alerts enabled, a channel attached, outside a maintenance window), Supercheck opens an incident for it. This needs only `SRE_ENABLED` (on by default), not an AI provider, and happens even if the alert delivery fails.

| Rule | Behavior |
|---|---|
| **One incident per source** | While an incident for a monitor or job is open, further failures join it as linked alerts. If the check fails again after a *recovered* note, the timeline shows **Failure returned** and the next recovery is noted again |
| **Alert snapshot** | Each incident keeps the alert's message, severity and time as they were when it was linked, so a later failure of the same check does not change an older incident's evidence |
| **Severity** | *Auto* derives SEV1 to SEV4 from the alert; a fixed level in the check's settings overrides it |
| **Auto-resolve** | On recovery, an unacknowledged incident resolves itself with a note, even if recovery alerts are off. An acknowledged one stays open, gets a *recovered* note, and its participants are emailed. Applies to monitor-down and job failed or timed-out alerts; SSL-expiry incidents stay open until someone resolves them |
| **Reopen** | A new failure within 30 minutes of an automatic resolution reopens the same incident. A failure that fired before the recovery, but was processed after it, does not. Changing a resolved incident's status in **Edit** also reopens it and clears its acknowledgement |

Control this per check under **Alert Settings → Incidents**: **Open an incident when this alerts**, **Severity**, and **Resolve automatically on recovery if nobody acknowledged it** (both toggles on by default).

<Callout type="info">
AI triage is separate and optional. It runs only when an administrator enables automatic triage (`SRE_AUTOMATION_ENABLED`) and an AI provider is configured.
</Callout>

</Accordion>

<Accordion title="Ownership and Acknowledgement" id="ownership">

| Action | Behavior |
|---|---|
| **Default assignee** | Incidents opened from alerts are assigned to the primary owner of the linked service when that person is still a member who can act on incidents. Otherwise they stay unassigned |
| **Assign** | Choose any organization owner or admin, or a project admin or editor of this project. Viewers and people outside the project are rejected. Assigning again to the same person changes nothing |
| **Acknowledge** | Stamps who acknowledged and when. If the incident is unassigned, the acknowledger becomes the assignee. Acknowledging twice is harmless |
| **Commander** | Optional single incident commander, set from the sidebar |

Assignments, acknowledgements, status changes, and resolution all appear on the timeline and in the audit log.

</Accordion>

<Accordion title="Incident notifications" id="notifications">

Supercheck announces an incident when it is **opened**, **assigned**, **acknowledged**, gets an **AI finding**, **reopens**, or is **resolved**.

| Where | What is sent |
|---|---|
| **The check's channels** | Assignment, acknowledgement, AI findings, and resolution or reopening by a person. Opening, recovery, automatic resolution and automatic reopening post nothing extra, because the worker's alert and recovery already went there. If every delivery of the opening alert failed, the channels get the incident-opened message instead |
| **Participant email** | The assignee and the incident commander get a direct email for every change someone else makes: assignment, acknowledgement, resolution and reopening, plus recovery and automatic reopening. On a reassignment the previous assignee is told too. You are never emailed about your own change, and only people who can still act on the incident (owners, admins, and the project's admins and editors) receive mail. Requires email delivery |
| **Incidents created by hand** | No source channels, so only the participants are emailed |

Email, Slack, Teams, Discord, Telegram and plain webhook channels are supported; webhooks with a preset or body template are skipped for incident messages. Each message names the incident, severity and service and links to it, without raw evidence, logs, credentials or AI conclusions. The same event is announced once within a short window, and recovery and reopen emails reach each person at most once every 10 minutes, so a flapping check does not flood inboxes.

</Accordion>

<Accordion title="Incident Lifecycle" id="lifecycle">

| Stage | Who | Action |
|---|---|---|
| **Triage** | Responder / Supercheck | An incident opens automatically from an alert (or create one manually). AI triage and correlation depend on administrator configuration |
| **Investigate** | AI SRE agent | Reads native evidence and authorized connectors, then generates cited hypotheses |
| **Decide and fix** | Responder | Evaluates findings and applies remediation in external systems |
| **Confirm recovery** | Responder | Re-runs synthetic tests, checks monitors, or observes metrics |
| **Acknowledge** | Responder | Select **Acknowledge** to take ownership; the incident is assigned to you if nobody else holds it |
| **Resolve** | Responder | Select **Resolve incident**. A resolution summary is required (up to 2,000 characters) and is pre-filled from the AI root cause when one exists. Edit it to state the fix and the checks that confirmed recovery |

Resolving records your decision and the summary on the incident and its timeline. It does not run checks or apply remediation. Closing an incident through the edit dialog is not available; use **Resolve incident**.

</Accordion>

<Accordion title="Incident Trends" id="trends">

| Metric | Shows |
|---|---|
| **Volume** | Incidents created vs. resolved |
| **Resolution rate and average resolution time** | Percentage resolved and mean time to resolution |
| **Severity mix** | Breakdown across SEV1 to SEV4 |

<Accordion title="Permissions" id="permissions">

| Role | View | Investigate stored evidence | Live sources | Assign, acknowledge, resolve, post updates |
|---|:---:|:---:|:---:|:---:|
| Org Owner, Org Admin, Project Admin | ✓ | ✓ | ✓ | ✓ |
| Project Editor | ✓ | ✓ | — | ✓ |
| Project Viewer | ✓ | — | — | — |

The same `sre_incident:update` permission covers assign, acknowledge, resolve, and updates over the API (`POST /api/sre/incidents/{id}/assign`, `/acknowledge`, `/resolve`).

If investigations are disabled, existing evidence and results stay readable, but run and live-source controls are unavailable.
