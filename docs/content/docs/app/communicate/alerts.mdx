Notifications tell your team when monitors fail, jobs break or services recover. **Communicate → Notifications** has two tabs: **Channels** and **Delivery history**.

![Notification Channels](/screenshots/notification-channels.png)

## Set up a channel

<Brands names={["slack", "teams", "discord", "telegram", "webhook"]} />

![Create a notification channel](/screenshots/notification-channel-dialog.png)

Email uses your SMTP provider; the others use the service's webhook or bot token. Paging services (PagerDuty, Jira Service Management, Splunk On-Call, Better Stack, incident.io) are webhook channels with a [preset](#webhook-presets): a failure opens a page and the recovery resolves it.

<Steps>
<Step>
### Create the channel
Open **Communicate → Notifications → Channels** and select **Create channel**.
</Step>
<Step>
### Pick the type and enter its credentials
Email, Slack, Teams, Discord, Telegram, a paging service preset or a custom webhook. See [Channel settings](#provider-configuration).
</Step>
<Step>
### Test and save
Select **Test connection**, then save.
</Step>
<Step>
### Attach it
Select the channel in a monitor's or job's **Alert Settings**. Saving replaces the linked channels with your selection; channels linked through the API show there too.
</Step>
</Steps>

| Limit | Value |
|---|---|
| Email test sends | 5 per 10 minutes per user, only to your own address or members of your organization, at most 5 recipients |
| Other test sends | 20 per 10 minutes per user |
| Deleting a channel | Blocked while a monitor or job uses it; remove it from them first |

<Accordion title="Self-hosted" id="self-hosted-smtp">

An administrator configures SMTP. Set `SMTP_USER` and `SMTP_PASSWORD` only when the server requires authentication; `SMTP_FROM_EMAIL` is always required.

```bash
SMTP_HOST=smtp.resend.com
SMTP_PORT=587
SMTP_FROM_EMAIL=alerts@yourdomain.com
SMTP_USER=resend            # optional, set both or neither
SMTP_PASSWORD=your-api-key  # optional
SMTP_BLOCKED_RECIPIENT_DOMAINS=qa.yourdomain.com  # optional, comma-separated, subdomains included
```

Reserved domains that cannot receive mail are always skipped, not bounced: `example.com`, `example.net`, `example.org`, and anything under `.example`, `.invalid`, `.test` or `.localhost`. Use `SMTP_BLOCKED_RECIPIENT_DOMAINS` for more, such as a test domain without an MX record.

**Supported providers:** Resend, SendGrid, Mailgun, Amazon SES, Gmail, Office 365

## Webhooks and paging services [#webhook-presets]

Presets fill the method, headers and JSON body for common incident tools. Each asks only for its own credential; the URL, method, headers and body stay editable under **Advanced**. Notification credentials are separate from any [read-only investigation connector](/docs/app/investigate/connectors).

| Preset | Use case | Credential | Setup docs |
|---|---|---|---|
| Custom webhook | Default Supercheck payload or a custom JSON template | Optional headers | [Supercheck alerts](/docs/app/communicate/alerts) |
| PagerDuty Events API v2 | Trigger and resolve incidents using `{{pagerDutyEventAction}}` and `{{dedupKey}}` | **Routing key** (written into the body template) | [PagerDuty Events API v2](https://developer.pagerduty.com/docs/events-api-v2/overview/) |
| Jira Service Management | Creates alerts with an alias, sent to `api.atlassian.com/jsm/ops/integration/v2/alerts` with `Authorization: GenieKey <integration key>`; recovery closes the alert by alias | **API key** (sent as `Authorization`) | [JSM integration events](https://developer.atlassian.com/cloud/jira/service-desk-ops/rest/v1/api-group-integration-events/) |
| Splunk On-Call REST endpoint | Send VictorOps/Splunk On-Call `CRITICAL` and `RECOVERY` events | Endpoint **URL** | [Splunk On-Call REST Endpoint](https://help.victorops.com/knowledge-base/rest-endpoint-integration-guide/) |
| Better Stack webhook | Sends `status: alert` on failure and `status: resolved` on recovery with `dedup_key`. In Better Stack, set the create rule to "status contains alert", the resolve rule to "status contains resolved" and the alert id to `dedup_key` | Endpoint **URL** | [Better Stack incoming webhooks](https://betterstack.com/docs/uptime/incoming-webhooks/) |
| incident.io alert source | Sends `status: firing` on failure and `status: resolved` on recovery with `deduplication_key` | Endpoint **URL** and **API token** (sent as `Authorization`) | [incident.io alert sources](https://docs.incident.io/alerts/alert-sources) |

<Callout type="warn">
Preset payloads include placeholders such as `REPLACE_WITH_PAGERDUTY_ROUTING_KEY` and `REPLACE_WITH_JSM_INTEGRATION_KEY`. The typed credential fields replace them; a channel that still holds one is rejected. Check the endpoint URL in the vendor docs, because some providers generate tenant-specific URLs.
</Callout>

## Alert types

Each failure alert also opens an incident unless you turn that off in the check's **Incidents** settings. See [How alerts become incidents](/docs/app/investigate/incidents#how-alerts-become-incidents).

<Tabs items={['Monitors', 'Jobs']}>
<Tab value="Monitors">

| Alert | Trigger | Severity |
|-------|---------|----------|
| **Failure** | Consecutive failures reach threshold | Error |
| **Recovery** | Consecutive successes reach threshold after the failure threshold was reached | Success |
| **SSL Expiring** | Website monitor's certificate is within its warning window, has expired, or could not be read for 24 hours | Warning; at most once every 24 hours |
| **SSL Renewed** | A certificate you were warned about is healthy again: valid with more days left than the warning window, or a later expiry date than the one warned about | Success; once per warning |
| **Warning** | A warning you turned on for the monitor, such as **Ping is late** on a [heartbeat monitor](/docs/app/heartbeat) | Warning; once per episode, never opens an incident |

A down MCP monitor, including a rejected login, is a normal **Failure** and opens a `sev2` incident by default.

</Tab>
<Tab value="Jobs">

| Alert | Trigger | Severity |
|-------|---------|----------|
| **Failure** | One or more tests in the job failed | Error |
| **Success** | All tests passed and consecutive successes reach the recovery threshold (optional) | Success |
| **Timeout** | Job exceeded maximum execution time | Warning |

</Tab>
</Tabs>

## Threshold configuration

**Failure Threshold** is the number of consecutive failures before the first failure alert; **Recovery Threshold** is the number of consecutive healthy checks before the recovery alert. Both accept 1–5 in the app and 1–100 in the API. A monitor that never reached the failure threshold sends no recovery alert. Thresholds keep network blips from alerting.

Example with Failure Threshold 3 and Recovery Threshold 2:

| Check | Result | Consecutive Count | Alert Sent |
|-------|--------|-------------------|------------|
| 1 | Fail | 1 failure | — |
| 2 | Fail | 2 failures | — |
| 3 | Fail | 3 failures | **Failure Alert** |
| 4 | Fail | 4 failures | — |
| 5 | Pass | 1 success | — |
| 6 | Pass | 2 successes | **Recovery Alert** |

Check 4 sends nothing because the next reminder waits for the [alert limiting](#alert-limiting) gap. Check 5 resets the failure counter and starts the recovery counter.

### SSL alerts

Turning on **SSL Check** on a website monitor also turns on **Alert on SSL certificate expiration** (you can switch it off). SSL notices are separate from the monitor's up/down result and use its **Alert in _N_ days** window.

| Notice | Sent when | How often |
|---|---|---|
| **SSL Expiring** | The certificate is inside the window or expired | At most once every 24 hours |
| **SSL Expiring** (unreadable) | The site is up but the certificate could not be read for 24 hours. A single failed read sends nothing | At most daily |
| **SSL certificate renewed (valid until _date_)** | After a warning, a check finds a valid certificate outside the window or with a later expiry | Once per warning |
| **SSL certificate readable again** | After an unreadable warning, the certificate can be read | Once per warning |

- Renewed and readable notices show as **SSL Renewed** in delivery history, go to the same channels, and never open or resolve an incident. Webhooks receive them as a resolve event with the same `ssl:` key as the warning.
- A failing channel is retried up to 5 times, then skipped. Turning off SSL alerts or **SSL Check** discards a pending notice.
- During a [maintenance window](/docs/app/monitor#maintenance-windows), failure, recovery, SSL and SSL renewed notices are held back (renewed notices are sent after the window). Checks still run and count toward uptime.

### Alert limiting

At most **3 failure alerts** go out per failure streak, for monitors and jobs: the first at the failure threshold, then reminders. With `N = max(5, 2 × threshold)`:

- **Jobs:** a reminder after every further `N` failures.
- **Monitors:** the first reminder `N` failures after the first alert, the second `2N` after that. An undeliverable alert is retried on the next checks for up to `N` checks, and the next gap counts from when it was sent.
- The interval is not configurable. A passing run resets the streak, and each recovery sends one alert.

Each channel normally gets an alert once: if one channel fails, only it is retried (up to 5 attempts), and retried checks or parallel workers do not resend. In rare failures (a worker stopping mid-send, a database error while recording the delivery, an upgrade) a channel can get an alert twice, so integrations should de-duplicate on the alert's dedup key.

## Warnings

Warnings report a problem that is not an outage yet. They:

- never open or resolve an incident and are never sent to paging services;
- don't count toward failure or recovery thresholds;
- are held back during [maintenance windows](/docs/app/monitor#maintenance-windows).

Turn them on per monitor under **Warnings** in the alert settings; only warnings that apply to the monitor type are listed. **Ping is late** is off by default. The MCP and AI endpoint warnings are on, but the slow and token warnings send nothing until you set their limit.

| Warning | Monitor type | Sent when |
|---|---|---|
| **Ping is late** | Heartbeat | A ping has not arrived on time, but the grace period has not ended. Sent once per late period. If the grace period ends without a ping, the monitor goes down and the normal failure alert follows |
| **Tools changed** (`mcp_tools_changed`) | MCP | The server's tool list, a tool description or an input schema changed since the last check. Sent once per change |
| **MCP slow** (`mcp_slow`) | MCP | Checks were slower than **Slow after (ms)** for 3 checks in a row. Sent once per slow stretch |
| **Slow first token** (`ai_slow_first_token`) | AI Endpoint | The first token was slower than **Warn when first token is slower than (ms)** for 3 checks in a row. Sent once per slow stretch |
| **Model changed** (`ai_model_changed`) | AI Endpoint | The reply came from a different model than the last check. Sent once per new model |
| **Single failed agent run** (`agent_run_failed`) | Synthetic, agent test | A run of an agent test failed but the failure threshold is not reached yet. On by default. Sent once per failed streak; the incident follows when the threshold is reached |
| **Tokens high** (`ai_tokens_high`) | AI Endpoint | A reply used more tokens than **Warn when a call uses more tokens than**. Sent once per stretch |

| Where | What a warning looks like |
|---|---|
| Delivery history | Type **Warning** |
| Email | Subject starts with "Warning:" |
| Every message | "This is a warning. No incident was opened." |
| Custom webhook | `type: "monitor_warning"`, `severity: "warning"`, `warningKind` (e.g. `heartbeat_late`), action `trigger`, dedup key `warning:<monitor id>:<kind>` |
| Monitors-as-code | `alertConfig.warnings`, e.g. `warnings: { heartbeat_late: true }` |

## Test and troubleshoot delivery

### Test a page

<Steps>
<Step>
On **Communicate → Notifications → Channels**, open the channel's menu and select **Send test page** (webhooks and paging services) or **Send test message** (other channels). Saved secrets are reused.
</Step>
<Step>
Confirm with **Send test page** in the dialog. A test page is a real page and can wake whoever is on call.
</Step>
<Step>
For a paging service, **Resolve test page** closes it again, including one left open by an earlier test.
</Step>
</Steps>

- A webhook test shows the receiver's HTTP status, the time it took, the first 1,024 characters of its response (credentials redacted) and the dedup key `test:<channel id>`.
- Editors and above can send tests, within the same per-user limits as **Test connection**. A successful test clears **Check the integration key**.
- CLI: `supercheck notification test <id>` and `supercheck notification test <id> --resolve`.

### If a page fails

| Response | Retried? | Result |
|---|---|---|
| HTTP 429, 5xx or network error | Up to 3 times, honouring `Retry-After` up to 10 seconds | — |
| HTTP 400 or 404 | No | Delivery fails |
| HTTP 401 or 403 | No, and not on later checks either | Channel shows **Check the integration key** until a delivery succeeds |

A channel whose latest delivery in the past 7 days was rejected with 401 or 403 shows **Check the integration key**; any other failed latest delivery shows **Last delivery failed**.

When a paging service still fails and the check opens an incident:

- the incident timeline records the failed page;
- the incident message goes to the project's Default policy channels;
- if nothing reaches anyone and the incident has no owner who can act, the project's owners and admins are emailed.

<Callout>
Monitors that page only a paging service and open no incidents have no fallback. Add an email or chat channel to them too.
</Callout>

### One-way paging

- Supercheck sends trigger and resolve events only. Acknowledging or closing the page in the paging service does not change the Supercheck incident, so acknowledge or resolve it in Supercheck too.
- Incident reminders and escalation are never sent to paging services; the service repeats and escalates its own page.
- A job's page resolves once, on the first passing run after the failure (past its recovery threshold), whether or not **Alert on success** is on. Later passing runs send nothing.

## Delivery history

**Notifications → Delivery history** lists the latest 200 alert notifications (not incident updates).

![Alert History](/screenshots/alert-history.png)

| Column | Shows |
|---|---|
| **Alert ID** | Short ID, click to copy |
| **Title** | Monitor or job name |
| **Type** | Alert type, and the warning kind for warnings |
| **Status** | Delivery status. Hover it for each webhook attempt's HTTP status or error and duration |
| **Incident** | The incident the alert belongs to, linked. A sent failure alert with no incident (for example, incidents turned off for that check) shows **Open incident** to create one. See [How alerts become incidents](/docs/app/investigate/incidents#how-alerts-become-incidents) |
| **Provider** | Channel type or preset used |
| **Sent At** | When it was sent |

Each row also keeps delivery metadata for AI SRE correlation (provider or preset, dedup key, event action, response status, attempt count, response hash). Raw provider response bodies and credentials are never shown.
