Variables give your tests configuration, credentials and test data at runtime.

![Variables List](/screenshots/variables-list.png)

<Callout type="info">
Use file variables for non-sensitive test data and fixtures. Keep passwords, API keys, and tokens in **Secrets**, not inside uploaded files.
</Callout>

## Variables vs Secrets vs Files

| Choose | Use for | Read in a test | Visibility |
|---|---|---|---|
| **Variable** | URLs, timeouts, configuration | `getVariable('KEY')` | Plain text in the dashboard and output. |
| **Secret** | Passwords, API keys, tokens | `getSecret('KEY')` | Encrypted at rest; revealing requires permission. Avoid logging it. |
| **File** | CSV, JSON, YAML, XML, TSV, or text fixtures up to 5 MB | Playwright: `readFile('KEY')`; k6: `open(getFile('KEY'))` during init | Uploaded test data; do not include credentials. |


## Creating Variables

<Steps>
<Step>

Open your project's **Variables** page and select **Add Variable**.

</Step>
<Step>

Choose the **Type**, then enter a **Variable Name** and its value.

| Type | Key example | Value |
|---|---|---|
| **Variable** (default) | `BASE_URL` | Plain text, e.g. `https://staging.example.com` |
| **Secret** | `API_KEY` | Text, encrypted and masked |
| **File** | `TEST_DATA` | Upload CSV, JSON, YAML, XML, TSV or plain text, max 5 MB |

</Step>
<Step>

Optionally add a **description** for your team, then select **Add Variable**.

</Step>
</Steps>

![Add Variable dialog with Type set to Variable](/screenshots/add-variable.png)

![Add Variable dialog with Type set to Secret and a masked value](/screenshots/add-secret.png)

<Callout type="info">
Secret values are masked in the UI. Users with secret-view permission can reveal a value with the audited reveal action (refused while a super admin is impersonating a user). Converting a secret back to a variable requires a replacement value.
</Callout>

<Accordions>
<Accordion title="Using and rotating file variables" id="file-variables">

In Playwright, `readFile(key)` returns the contents. In k6, use `open(getFile(key))` in the init context, and prefer `SharedArray` for datasets shared across VUs. To rotate a dataset without changing scripts, keep the key and upload a replacement file.

</Accordion>
</Accordions>

## Using Variables in Tests

Access variables and secrets in your test code using the built-in functions:

<Tabs items={['getVariable()', 'getSecret()', 'readFile()', 'getFile()']}>
<Tab value="getVariable()">

Use for non-sensitive configuration:

```javascript

// Basic usage
const baseUrl = getVariable('BASE_URL');
const timeout = getVariable('TIMEOUT');

// Navigate using variable
await page.goto(baseUrl + '/login');
```

</Tab>
<Tab value="getSecret()">

Use for sensitive credentials:

```javascript

// API authentication
const apiKey = getSecret('API_KEY');
await page.setExtraHTTPHeaders({
  'Authorization': `Bearer ${apiKey}`
});

// Form login
const password = getSecret('TEST_PASSWORD');
await page.fill('#password', password);

// Database connection
const dbPassword = getSecret('DB_PASSWORD');
```

</Tab>
<Tab value="readFile()">

Use in Playwright and other Node.js-based test execution when you want the uploaded file contents as a string:

```javascript
const playwrightCsvContent = readFile('TEST_DATA');

const rows = playwrightCsvContent
  .split('\n')
  .slice(1)
  .filter(Boolean)
  .map((row) => row.split(','));

for (const [name, email] of rows) {
  await page.fill('#name', name);
  await page.fill('#email', email);
}
```

</Tab>
<Tab value="getFile()">

Use in k6 when you need the resolved file path and want k6 to load the file during init context:

```javascript

// k6
const k6CsvContent = open(getFile('TEST_DATA'));

// Playwright path-based usage
const configPath = getFile('CONFIG_FILE');
```

</Tab>
</Tabs>

<Callout type="warn">
`readFile()` is for Playwright and other Node.js-based execution. k6 does not support `readFile()`. For k6, always use `open(getFile('KEY'))` during init context.
</Callout>

### Secret Protection

Use `getSecret()` when a test needs a credential. Execution output masks secret values, but you should still avoid logging them:

```javascript

// Avoid intentional secret logging in scripts
// Worker redaction is an additional protection layer for accidental output
console.log('API key configured:', !!getSecret('API_KEY'));

const actualKey = getSecret('API_KEY');
```

<Callout type="warn">
Masking covers console output, error messages, and text report files (`.html`, `.json`, `.txt`, `.md`, `.xml`, up to 20 MB each). It does not cover traces, screenshots, videos, or the Playwright HTML report, whose test data is stored compressed inside the page. If a test types a secret into a page, the secret can appear in those artifacts. Do not type secrets into pages whose reports you share.
</Callout>

<Accordions>
<Accordion title="What is masked" id="secret-masking">

- Secret values are replaced with `[SECRET]` in console output and errors. They are also replaced in `.html`, `.json`, `.txt`, `.md`, and `.xml` report files, including base64, URL-encoded, and JSON-escaped forms of each value. Files over 20 MB are not masked.
- Secrets shorter than 6 characters are not masked, because replacing short strings would damage unrelated output. Use longer secrets.
- Binary or compressed artifacts are not scanned or rewritten: `trace.zip`, screenshots, videos, and the test data embedded in the Playwright HTML report.
- If a script uses a secret that cannot be decrypted, the run fails with a message naming the key. k6 runs, and scripts that call `getSecret` with a non-literal key, read every project secret, so any undecryptable secret can fail them.

</Accordion>
</Accordions>

**Secrets work normally in:**
- Playwright actions (`page.fill()`, `page.click()`)
- HTTP headers and request bodies
- URL parameters
- Comparisons and conditionals

## Common Patterns

<Tabs items={['Environment-Based', 'API Testing', 'Database Testing', 'Feature Flags', 'k6 Performance', 'Data-Driven (File)']}>
<Tab value="Environment-Based">

```javascript
const env = getVariable('ENVIRONMENT'); // 'staging' or 'production'
const baseUrl = getVariable(`${env.toUpperCase()}_URL`);

await page.goto(baseUrl);
```

</Tab>
<Tab value="API Testing">

```javascript
const apiUrl = getVariable('API_URL');
const apiToken = getSecret('API_TOKEN');
const apiKey = getSecret('API_KEY');

const response = await request.get(apiUrl + '/users', {
  headers: {
    'Authorization': `Bearer ${apiToken}`,
    'X-API-Key': apiKey
  }
});
```

</Tab>
<Tab value="Database Testing">

```javascript
import { Pool } from 'pg';

const pool = new Pool({
  host: getVariable('DB_HOST'),
  port: parseInt(getVariable('DB_PORT')),
  database: getVariable('DB_NAME'),
  user: getVariable('DB_USER'),
  password: getSecret('DB_PASSWORD')
});
```

</Tab>
<Tab value="Feature Flags">

```javascript
const featureEnabled = getVariable('ENABLE_NEW_CHECKOUT') === 'true';

if (featureEnabled) {
  await page.click('[data-testid="new-checkout"]');
} else {
  await page.click('[data-testid="classic-checkout"]');
}
```

</Tab>
<Tab value="k6 Performance">

```javascript
import http from 'k6/http';

export default function () {
  const baseUrl = getVariable('API_URL');
  const apiKey = getSecret('API_KEY');
  
  http.get(`${baseUrl}/protected`, {
    headers: { Authorization: `Bearer ${apiKey}` }
  });
}
```

</Tab>
<Tab value="Data-Driven (File)">

```javascript
const csv = readFile('USER_DATA');
const users = csv
  .split('\n')
  .slice(1) // Skip header row
  .filter(line => line.trim())
  .map(line => {
    const [name, email, role] = line.split(',');
    return { name, email, role };
  });

// Test each user from the data file
for (const user of users) {
  await page.goto(getVariable('BASE_URL') + '/admin/users');
  await page.click('button:has-text("Add User")');
  await page.fill('#name', user.name);
  await page.fill('#email', user.email);
  await page.selectOption('#role', user.role);
  await page.click('button[type="submit"]');
  await expect(page.locator('.toast-success')).toBeVisible();
}
```

</Tab>
</Tabs>

## Best Practices

<Accordions>
<Accordion title="File variable best practices" id="file-variable-best-practices">

- Use file variables for reusable datasets and fixtures, not secrets or credentials
- Keep files small and text-based; split large datasets or generate them dynamically when needed
- Prefer JSON for nested structured data and CSV/TSV for tabular records
- Validate and parse uploaded content defensively before using it in tests
- Avoid logging full dataset contents in CI or shared environments unless you explicitly need that output

</Accordion>
<Accordion title="Variable naming conventions" id="variable-naming-conventions">

Names must follow these rules:

- 4 to 20 characters.
- Start with an uppercase letter, then use only uppercase letters, numbers, and underscores.
- Cannot start with `SUPERCHECK_`, which is reserved.
- Cannot be `PATH`, `HOME`, `USER`, `NODE_ENV`, or `PORT`.

Use clear, consistent naming for your variables:

| Pattern | Example | Use For |
|---------|---------|---------|
| `SCREAMING_SNAKE_CASE` | `BASE_URL`, `API_KEY` | Standard convention |
| `ENV_SPECIFIC` | `STAGING_URL`, `PROD_API_KEY` | Environment-specific values |
| `SERVICE_NAME` | `STRIPE_API_KEY`, `SENDGRID_KEY` | Third-party service credentials |

**Recommended variable names:**

| Variable | Description |
|----------|-------------|
| `BASE_URL` | Application base URL |
| `API_URL` | API endpoint base URL |
| `TIMEOUT` | Default timeout in milliseconds |
| `TEST_USER_EMAIL` | Test account email |
| `TEST_USER_PASSWORD` | Test account password (secret) |
| `API_KEY` | API authentication key (secret) |
| `DB_CONNECTION_STRING` | Database connection (secret) |

</Accordion>
</Accordions>

## Security Features

<Tabs items={['Encryption', 'Access Control', 'Audit Trail']}>
<Tab value="Encryption">

Store credentials as **Secrets** to encrypt saved values. Editing a secret starts with an empty value field; leave it blank to keep the current value, or select **Reveal current value** to view it. Keep secrets out of uploaded data files.

<Accordions>
<Accordion title="Changing the encryption key" id="encryption-key">

Secrets are encrypted with the instance's `SECRET_ENCRYPTION_KEY`. If you change it, existing secrets can no longer be decrypted, and runs that use them fail. Key rotation is not supported yet. Re-enter each secret after changing the key, and do not change it on an instance that has secrets you need.

</Accordion>
</Accordions>

</Tab>
<Tab value="Access Control">

Variables follow your project's role-based permissions:

| Role | View | Create | Edit | Delete | View Secret Values |
|------|------|--------|------|--------|-------------------|
| **Super Admin** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Org Owner** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Org Admin** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Project Admin** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Project Editor** | ✅ | ✅ | ✅ | ❌ | ✅ |
| **Project Viewer** | ✅ | ❌ | ❌ | ❌ | ❌ |

</Tab>
<Tab value="Audit Trail">

Creating, updating, renaming, deleting, and converting variables, in the app or through the CLI and API, is recorded in the audit log as `variable_created`, `variable_updated`, or `variable_deleted`. Each entry records who made the change, when, the project, the variable key (plus the previous key on a rename), and whether it is a secret. Values are never recorded. Revealing a secret is audited separately.

</Tab>
</Tabs>
