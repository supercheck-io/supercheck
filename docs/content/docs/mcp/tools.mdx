Read tools are marked `readOnlyHint: true`; the optional tools below are not. Every tool is limited to the project of the connection.

Returned text (test titles, error excerpts, incident summaries, investigation findings) comes from your systems and is treated as **untrusted data**: tool descriptions tell the AI never to follow instructions found in it.

## Scopes and tools

| Scope | Granted | Tools | Your role must also allow |
|---|---|---|---|
| `mcp:read` | Always | The 21 read tools below | Viewing that resource type |
| `mcp:incidents:write` | Optional | `assign_incident`, `acknowledge_incident`, `resolve_incident` | Updating incidents |
| `mcp:sre` | Optional | `triage_incident`, `investigate_incident`, `generate_incident_brief` | Investigating incidents (billable, uses AI credits) |

## Read tools

| Tool | Needs permission to view | Arguments | Returns |
|---|---|---|---|
| `get_context` | project | none | The connected project, your role and the scopes this connection holds |
| `list_tests` | tests | `limit`, `cursor`, `type`, `priority`, `search` | `id`, `title`, `type`, `priority`, `updatedAt` (no scripts) |
| `get_test` | tests | `id` | Metadata and description for one test (no script) |
| `list_jobs` | jobs | `limit`, `cursor` | `id`, `name`, `jobType`, `status`, `cronSchedule`, `lastRunAt`, `nextRunAt` (no alert settings) |
| `get_job` | jobs | `id` | One job plus its test IDs (up to 100) and which alerts are on (`enabled`, `alertOnFailure`, `alertOnSuccess`, `alertOnTimeout`, `incidentEnabled`, `incidentSeverity`, `autoResolveIncident`). No notification channels, trigger keys or scripts |
| `list_runs` | runs | `limit`, `cursor`, `status`, `jobId` | Recent runs, newest first: `status`, `trigger`, `location`, `durationMs`, start and end |
| `get_run` | runs | `id` | One run plus a redacted, truncated `error` excerpt |
| `list_monitors` | monitors | `limit`, `cursor` | `name`, `type`, `target` (scheme and host only), `status`, `lastCheckAt` |
| `get_monitor` | monitors | `id` | One monitor: `target` (scheme and host only), `status`, `enabled`, `frequencyMinutes`, `locations` (with `locationStrategy` and `locationThreshold` when multi-location checks are on) and non-secret check settings (`method`, `expectedStatusCodes`, `port`, `protocol`, `timeoutSeconds`, `enableSslCheck`) and which alerts are on, including `incidentEnabled`, `incidentSeverity` and `autoResolveIncident`. No headers, auth, request body or notification channels |
| `list_requirements` | requirements | `limit`, `cursor`, `coverageStatus` | `id`, `title`, `priority`, `coverageStatus` (`covered`, `failing`, `missing`), `linkedTestCount`, `updatedAt` |
| `get_requirement` | requirements | `id` | One requirement with description, tags, external ID and link, coverage counts and its linked tests (up to 100) |
| `list_status_pages` | status pages | `limit`, `cursor` | `name`, `status`, `subdomain`, `customDomain`, `customDomainVerified`, `headline` |
| `get_status_page` | status pages | `id` | One status page plus its components and their monitor IDs. Never subscribers |
| `list_services` | services | `limit`, `cursor` | Service catalog: `name`, `description`, `tier`, `environment`, `ownerTeam`, `tags`, `status` |
| `get_service` | services | `id` | One service plus its dependencies in both directions, owning teams, repository host and latest health |
| `list_variables` | variables | `limit`, `cursor` | `key`, `type`, `isSecret`, `description`, `updatedAt`. Never values |
| `list_incidents` | incidents | `limit`, `cursor`, `status`, `severity`, `assignee` | `number`, `title`, `severity`, `status`, `statusLabel`, `createdAt`, `resolvedAt`, `assigneeUserId`, `commanderUserId`, `acknowledgedAt`, `acknowledgedByUserId`, `mitigatedAt` |
| `get_incident` | incidents | `id` | One incident with `statusLabel`, its root-cause summary, resolution summary, assignment and acknowledgement, and `alertCount` (linked alerts) |
| `list_investigations` | investigations | `limit`, `cursor`, `incidentId` | AI SRE investigation runs: `agentType`, `status`, start and end, `durationMs`, `confidenceScore` |
| `get_investigation` | investigations | `id` | One investigation with its root-cause hypothesis and recommendations |
| `prepare_local_authoring` | project | none | CLI commands for creating or editing tests, requirements and status pages (this server does not author tests) |


## Optional tools

Registered only when the connection holds the scope. Calls are recorded in the audit log (ids and timing, never arguments).

| Tool | Scope | Needs permission | Arguments | Does |
|---|---|---|---|---|
| `assign_incident` | `mcp:incidents:write` | update incidents | `id`, `assigneeUserId` (or `null` to unassign), `role` (`assignee` or `commander`) | Assigns the incident or sets its commander |
| `acknowledge_incident` | `mcp:incidents:write` | update incidents | `id` | Acknowledges it, claiming it for you if unassigned |
| `resolve_incident` | `mcp:incidents:write` | update incidents | `id`, `resolutionSummary` (up to 2000 characters) | Resolves it with a summary |
| `triage_incident` | `mcp:sre` | investigate incidents | `incidentId` | Starts AI triage |
| `investigate_incident` | `mcp:sre` | investigate incidents | `incidentId`, `useLiveConnectors`, `guidance` | Starts a full investigation. Live connectors also need connector investigate permission |
| `generate_incident_brief` | `mcp:sre` | investigate incidents | `incidentId` | Generates an evidence brief |

The write tools behave like the dashboard: notifications and timelines are the same. The `mcp:sre` tools use AI credits and apply the same checks as the dashboard (AI SRE enabled, plan, daily AI limit, rate limits). They return `accepted: true` at once; poll `list_investigations` with `incidentId`, then `get_investigation`. A Copilot chat is not available over MCP.

<Accordions>
<Accordion title="Paging" id="paging">

List tools accept `limit` (1 to 50, default 20) and `cursor`. When more results exist the response has a `nextCursor`; pass it back as `cursor` for the next page. `id` and `cursor` values are UUIDs.

</Accordion>
<Accordion title="Errors" id="errors">

| Code | Meaning |
|---|---|
| `forbidden` | Your role cannot view this kind of resource |
| `not_found` | No such item in the connected project |
| `internal_error` | The request failed; try again |
| `rate_limited`, `daily_limit`, `subscription_required`, `unavailable`, `feature_disabled` | An `mcp:sre` start was refused by the same limits and plan checks as the dashboard |
| `invalid`, `conflict` | An incident write was refused (for example an assignee who cannot act on incidents) |

Invalid arguments (an `id` that is not a UUID, or a `limit` outside 1 to 50) return a validation error. Connection-level problems return HTTP errors instead, each as a JSON-RPC error with the code in `error.data.code`: `400` (`parse_error` when the body is not JSON, `batch_too_large` over 20 calls), `401` (sign in again), `403` (`access_denied` when access was removed, `invalid_request_origin`, or `insufficient_scope`), `404` (MCP is off), `405` (only POST is accepted), `413` (request over 1 MB), `429` (`rate_limited` or `too_many_concurrent_requests`, with `Retry-After`), `500` (`server_error`), `503` (`rate_limiter_unavailable` or `server_unavailable`, with `Retry-After` when the server can say when to retry).

`get_incident` takes the incident `id` from `list_incidents`, not the incident number.

Filters are optional and combine with paging. `list_runs` accepts `status` (`queued`, `running`, `passed`, `failed`, `error`, `blocked`) and `jobId`; `list_tests` accepts `type`, `priority` and `search` (case-insensitive title match); `list_incidents` accepts `severity` (`sev1` to `sev4`) and `status` (stored values, not `statusLabel`: `open` for every unresolved incident, or one of `triggered`, `investigating`, `identified`, `recommendations_ready`, `user_applying_fix`, `verifying`, `resolved`) and `assignee` (`me`, `unassigned` or a user id); `list_requirements` accepts `coverageStatus`; `list_investigations` accepts `incidentId`.

</Accordion>
<Accordion title="AI SRE" id="ai-sre">

Results AI SRE already produced (hypotheses, confidence, recommendations) are readable with the base scope. Starting AI work needs `mcp:sre`, and always runs asynchronously: the tool returns before the run ends, so poll for the result. Copilot chat stays in the dashboard and the CLI (`supercheck sre ask`).

</Accordion>
<Accordion title="Not available" id="not-available">

Creating, editing or deleting tests, monitors, jobs and variables, test scripts, variable values, monitor credentials and request settings, notification channels, status page subscribers, run reports and artifact files, investigation evidence and tool calls, and an incident timeline. Use the [CLI](/docs/cli/commands) for authoring and deploys.

</Accordion>
</Accordions>
