## You stay in control

- **You approve each connection** and choose the single project it can read.
- **Read-only by default.** Tools that change incidents (`mcp:incidents:write`) or start AI SRE work (`mcp:sre`) exist only when the app asked for that scope and you approved it. Nothing creates, edits or deletes tests, monitors, jobs or variables, and nothing triggers runs.
- **Disconnect works immediately.** Remove an app under **Account**, **Connected apps**. `/oauth2/revoke` revokes refresh tokens only; an access token keeps its signature for up to 15 minutes, but every call re-checks your approval, so Disconnect refuses it at once.
- **Approvals add up.** Approving again for the same app and project keeps every scope you approved before; a narrower request never removes a broader grant. Only Disconnect removes scopes. `mcp:read` is always required: a request without it is refused, and a request that names no scope at all is treated as `mcp:read` only.
- **Your role applies on every call.** Access is re-checked for each request, not only when you connect, so these take effect at once:
  - you disconnect the app
  - you are removed from the organization (if you are removed only from the project, you keep read-only access as a viewer while you remain in the organization)
  - your account is banned (and the ban has not expired)
  - your role can no longer view that kind of resource

## Sign-in design

| Property | Value |
|---|---|
| Protocol | OAuth 2.1 with PKCE (S256) and resource indicators |
| Scopes | `mcp:read` (always), optional `mcp:incidents:write` and `mcp:sre`, and `offline_access` for refresh. An optional tool works only while both your approval and the token carry its scope, and your role still allows the action |
| Access token | 15 minutes |
| Refresh token | 30 days, rotated on use. The previous token keeps working for 30 seconds, so a retry after a dropped response succeeds |
| Client registration | Public clients only, at most 5 registrations per minute per IP address |

<Accordions>
<Accordion title="What is filtered" id="what-is-filtered">

- Test scripts, variable values, notification channels, trigger keys, monitor credentials, headers and request bodies, status page subscribers, and investigation prompts, evidence and cost are never returned. Jobs show only which alerts are on, and monitors only non-secret check settings.
- Monitor targets are reduced to scheme and host, so URLs that hide a secret in the path or query stay hidden.
- Text is scanned for credentials (tokens, API keys, `Authorization` and cookie headers, URL passwords) and replaced with `[REDACTED…]` markers (including Supercheck's own API keys and email addresses), and long fields are cut off with `[truncated]`.
- Requests over 1 MB are rejected.

</Accordion>
<Accordion title="Prompt injection" id="prompt-injection">

Tests, logs and incidents can contain text written by someone else. Tool descriptions tell the AI to treat it as data. Keep that in mind when you give an AI tool other tools that can act (for example shell or deploy access), and review its actions.

</Accordion>
<Accordion title="Limits" id="limits">

Each connected app may send up to 300 requests a minute, and all of your connected apps together up to 600 (every call in a batch counts as one request). An app may have at most 4 requests running at a time, and you at most 8 across your apps. A batch carries at most 20 calls. Over a limit, the server answers `429` with `Retry-After`.

Resetting your password signs you out everywhere and disconnects every connected app. Reconnect the ones you still use. Job trigger keys used by pipelines are not affected.

</Accordion>
<Accordion title="Audit" id="audit">

Tool calls (user, app, project, duration) and access-denied events (user, app, reason) are written to the audit log. Arguments and results are not stored.

Self-hosted: see [Self-Hosted](/docs/app/deployment/self-hosted#connecting-ai-tools-mcp-off-by-default).

</Accordion>
